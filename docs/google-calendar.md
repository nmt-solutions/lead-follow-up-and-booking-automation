# Google Calendar appointment connection

Business Owners and Admins use **Business profile → Booking calendar connection** with a current verified MFA session. Google sign-in and mailbox permissions do not establish Calendar access. RFQ handling remains independent. This integration uses ordinary TypeScript and the existing appointment application; it does not add an auth plugin, scheduling service or worker retry of event creation.

## Operator setup

Use a real Google Cloud project with Calendar API enabled and a Web application OAuth client. Configure the consent screen, publishing/audience, authorized domains, privacy policy and actual verification/approval required by the chosen audience/scopes. Workspace administrators may also need to allow the app. Testing-mode restrictions, test-user allowlists and refresh-token lifetimes still apply; a configuration flag cannot replace Google's approval.

Set these server-only values through the deployment secret store:

- `GOOGLE_CALENDAR_CLIENT_ID`, `GOOGLE_CALENDAR_CLIENT_SECRET` for the dedicated Calendar client/project. Do not reuse a shared login/mail project if revocation isolation is required: Google revocation can invalidate the account's other grants to that project.
- `BETTER_AUTH_URL`: the app's canonical HTTPS origin (localhost HTTP is supported for development).
- `GOOGLE_CALENDAR_TOKEN_KEY_ID`: an operator-chosen key identifier, and `GOOGLE_CALENDAR_TOKEN_KEYS`: a JSON object mapping key identifiers to cryptographically random 32-byte keys encoded as 64 lowercase hexadecimal characters. Generate actual keys in the secret manager; example credentials do not activate the integration.
- `GOOGLE_CALENDAR_APPROVED=true` only after the actual project, OAuth audience and supported account setup are approved for the intended deployment. Until all configuration is present, settings explicitly report setup required and booking cannot access Google.

Register the exact callback URI for each Business that will connect: `{canonical-origin}/api/businesses/{businessId}/calendar/google/callback`. Google requires registered redirect URIs; no wildcard redirect is assumed. OAuth state is random, hashed in persistence, single-use, ten-minute limited and bound to the initiating actor, Business, session and connection generation. PKCE S256 and a confidential server-side code exchange are used. Redirects return only to that Business's calendar settings.

The requested scopes are `openid`, `email`, `calendar.calendarlist.readonly`, `calendar.events` and `calendar.events.freebusy` (Calendar scopes use the `https://www.googleapis.com/auth/` prefix). These permit account identity, authorized calendar selection, availability, event reconciliation and conditional cancellation. No Gmail scope is requested; no broad Calendar administration scope is needed. Granular consent must include all three Calendar scopes. Account identity comes from Google's userinfo endpoint, not client input. Reconnect must use the original Google subject; disconnect before changing accounts.

Supported accounts are Google consumer or Workspace accounts with an accessible dedicated calendar and full **owner** or **writer** access. Read-only, free/busy-only and `writerWithoutPrivateAccess` access are excluded. Calendar time zones must be valid IANA zones. This is not resource-attendee acceptance or delegated service-account scheduling. Calendar selection comes from the live authorized CalendarList; arbitrary IDs are rejected. Only the selected calendar is exposed to booking. Booking hours, duration, buffers, customer time zones, holds and automation policy remain explicitly configured in Appointments.

## Credentials and recovery

Access/refresh tokens and PKCE verifiers use AES-256-GCM with Business/connection-specific authenticated context. Tokens, client secrets and verifier plaintext never enter API/UI data or diagnostics. Forced Business RLS, current integration roles/MFA, restricted column grants and a composite Business/connection FK apply to the new tables. Connection/account/grant provenance remains separate from historical booking records.

Keep previous encryption keys in the key map during rotation. Set a new active ID/key; each refresh or successful reconnect re-encrypts credentials with the active key. OAuth verifiers retain their original key until consumed/expired; quarantined tokens from rejected consent retain their key until safe local disposal; they never authorize remote revocation. These tokens are encrypted separately and can never supply booking credentials. Removing a primary key early blocks decrypt/use/revoke; restore it before recovery. Backups also require the relevant keys under the operator's retention policy. Auth-secret rotation does not silently change the Calendar encryption key.

The shared PostgreSQL Business lock serializes token refresh, reconnect, calendar selection, booking and local disconnect. The revocation phase verifies the exact disabled connection/generation, so a delayed disconnect cannot revoke a replacement grant. Rotated refresh tokens are retained even when returned scopes are insufficient; an omitted refresh token on a normal refresh retains the existing token. An invalid grant/401 moves the connection to reconnect required. Missing scope or live permission/role loss disables use until repaired. Rate limits and malformed/unavailable responses never mean an empty calendar. Provider failures expose only classified safe reasons, with no provider body or URL in diagnostics. Ephemeral OAuth states cascade away on session deletion, preserving sign-out/revocation of copied credentials.

Disconnect first durably disables local booking and invalidates pending OAuth states. It revokes only the original attributed primary token after current actor/MFA and shared Gmail/Calendar-subject checks. Rejected callback tokens are disposed locally with a manual/incomplete outcome; shared adopted consent is left intact and explicitly labelled. The subject lock fences concurrent adoption, and an unknown primary revoke remains pending for a separately authorized safe retry. A failed revocation remains visibly pending, can be retried explicitly, and cannot reconnect or book in the meantime. Successful revocation deletes encrypted credentials. Existing events, policy history, requests, authoritative identities and attendance/cancellation evidence remain. Historical records do not transfer to a newly connected account/connection. Review and cancel active appointments before disconnecting, or manage their events externally and record established Business evidence.

Free/busy is checked immediately before insert. Insert uses a stable Google-compatible event ID derived from the committed booking intent, with private Business/connection/Opportunity/appointment/intent provenance. There are **no attendees**, `sendUpdates=none`, default reminders are disabled, and conferencing is not requested. Customer notification is separate. Cancellation refuses events with externally added attendees and uses the observed event ETag in `If-Match` with `sendUpdates=none`; review such exceptions manually.

No provider mutation is automatically retried. 403/429 limits, permission failures, 409/412 conflicts and ambiguous insert/cancel results enter the existing booking recovery contract with explicit reasons. A timeout, malformed creation response, or database failure after insert can only recover through a read of the original event identity and bounded overlapping-event reconciliation. A missing event is conservatively non-definitive: it does not authorize another insert. Confirmation requires a validated authoritative event and durable stored identity. Google does not provide an atomic free/busy-and-insert reservation across external writers, and its distributed ID collision semantics are not a universal exactly-once guarantee. Reconciliation observes external overlapping events, moves, deletions and revision conflicts; later external edits can still race any observation.

## Controlled live-check procedure — not execution evidence

No live OAuth, event creation, invitation, send or UI check is established by automated fixtures or this procedure. A human must perform the following only after actual project approval and authorized setup. Use a dedicated Google test account/calendar with no real customer data, no attendees, no default reminders, and a separate bounded Business/Opportunity. Record sanitized timestamps, Business/connection IDs, granted scopes/role, request/event identity, status transitions and cleanup result. Never capture tokens, authorization codes, cookies, client secrets or raw OAuth URLs.

1. Complete operator setup above; register the exact test Business callback and allow the dedicated account. Verify missing configuration reports setup required before enabling it. Confirm the app's real runtime DB uses `app_runtime`, forced RLS and the secured schema.
2. Sign in as its Owner/Admin, verify MFA, connect and approve the listed scopes. Expect calendar selection required with the correct Google account; mail permission alone must remain insufficient. Decline a Calendar scope in a separate bounded consent attempt and expect permission missing without bookable slots; reconnect with complete consent afterward.
3. Select the dedicated writable calendar. Expect calendar authorized. Configure explicit test hours, duration, buffers, hold lifetime and time zone in Appointments. Use one future local-day availability check. Verify one pre-existing busy test interval is unavailable and another interval is offered; include a timezone/DST boundary if that account's supported deployment needs it.
4. Create at most **one** test appointment request/booking. Expect a local request/hold, then confirmed only after the authoritative Google event is stored and reconciled. Verify in Google that the ID/provenance matches, no attendee/invite/conference/default reminder was created, and replaying the app booking command creates no second event. Customer communication must remain unsent.
5. Use an approved test proxy/fault injection in this isolated environment, if available, to drop only the insert response after acceptance. Do not enable any production auth bypass or retry switch. Expect ambiguous/requested, then read-only reconciliation to the original event and no second insert. If a controlled fault cannot be introduced safely, record this live case as **not run**; deterministic coverage is separate evidence.
6. Add a single overlapping external test event or move the test appointment externally, then reconcile. Expect an actionable conflict, never automatic replacement. Remove the overlap/restore the time and reconcile. Externally added attendees must prevent app cancellation; remove them before continuing. Cancel through the app and expect authoritative cancellation evidence; the historical event identity remains retained.
7. If token-expiry observation is feasible, wait for real access expiry and make one bounded read; expect a refresh without another consent screen. Do not edit production tokens or clocks. Otherwise mark live refresh/rotation **not run**. Simulated 429, invalid payloads and race cases remain deterministic fixture evidence unless separately observed under an approved test setup; never intentionally exhaust real quota.
8. Revoke app access in Google's account permissions, then check availability. Expect reconnect required or unavailable pending the next provider authorization response, no new event, and retained history. Reconnect with the original test account, then disconnect in the app. Expect booking disabled immediately, with remote success, shared consent or incomplete manual cleanup explicitly distinguished; retry only a pending attributed-primary revocation.
9. Remove the remaining dedicated test events, OAuth grants and test-only registered redirect URI as appropriate. Confirm zero unintended invitations/messages and no leftover active test reservation. Preserve sanitized audit evidence and mark UI/account/project acceptance separately. Do not add `tested` until the user verifies the intended flow.
