# Signed WhatsApp intake and manual activity

Issue #39 composes the customer-owned Meta connection with the existing shared inbox, buyer, message-level Opportunity associations, approved knowledge, qualification, RFQ/booking goals and human control. It introduces no outbound WhatsApp transport (#40), BSP, credit line, prepaid Meta credit or operator-paid Meta message cost.

## Enable and observe

An Owner/Admin with current MFA opens **Business → WhatsApp identity → Incoming messages and manual activity**, chooses the provider-receipt retention required by the agreed data policy, and selects **Enable incoming capture**. No retention period is prefilled. This requires current selected-account ownership/permission/number evidence, encrypted authorization, and the configured durable worker. Payment evidence and outbound eligibility are separate: missing payment proof or paid discovery geography does not reject otherwise authorized incoming inquiries.

The explicit enable command subscribes this app to the verified selected WABA through Meta's `POST /{WABA-ID}/subscribed_apps`, then rechecks the current actor, session and connection generation before saving capture. It never treats subscription success, OAuth, billing review or callback verification as observed message synchronization. Configure the approved app's HTTPS `/api/webhooks/whatsapp` callback and its `messages` and supported `smb_message_echoes` subscriptions in Meta. Set `META_WEBHOOK_VERIFY_TOKEN` through the secret configuration process; never put secrets in page fields. Deploy Trigger's `recover-whatsapp-intake` with the same restricted database/app configuration before confirming `META_INTAKE_WORKER_DEPLOYMENT_CONFIRMED`.

**Refresh capture status** shows separate evidence for authorized capture, an actual signed incoming message, supported app activity and sending. `readiness.inboundReady` requires an observed signed inquiry; `manualVisibilityReady` requires supported app evidence without unresolved work/gaps. `sendingReady` and aggregate `automationReady` remain false until #40 implements the independent sending path. “Supported app activity observed” is deliberately limited; it is not complete synchronization, universal linked-device coverage, media support, history authorization or provider delivery proof.

## Authentication and durable acceptance

The webhook verifies HMAC SHA-256 against the **exact bounded raw bytes** using the selected app secret and constant-time comparison before parsing JSON. GET verification separately checks the callback verification token. The signed WABA ID and number ID resolve only an explicitly enabled current connection using a narrowly scoped server database function. Payload `businessId`, display-number claims and contact names cannot choose Business context. Number origin is checked against the verified selected number before labeling an event Business App activity.

Only normalized, bounded activity is retained. The request commits scoped receipts, event keys, content fingerprints and selected connection generation before returning success. It never sends messages, calls a model, books, changes Opportunity control or invokes another provider in the webhook. Trigger's recurring recovery discovers pending receipts from persistence without embedding private payloads in job arguments. A new worker process resumes the same receipts; Business locks and atomic receipt/workflow updates prevent duplicate effects. Changed content under the same provider identity records a visibility gap rather than rewriting earlier evidence.

Runtime transactions retain forced RLS and current Business membership/capability checks. A removed enabling Owner/Admin, changed connection version, local disconnect or unavailable authorization stops future intake/worker authority. Previously stored inbox records remain readable under their own current membership rules. Minimal SECURITY DEFINER functions discover exact verified bindings/work and purge expired staging content; PUBLIC cannot execute them. They return no tokens or private message content. Client errors and diagnostics contain allowlisted codes and request IDs, never raw payloads, names, message bodies, credentials or caught provider errors.

## Shared purchasing needs and human control

WhatsApp supplies a peer identity rather than a purchasing-need identifier. The application preserves the exact message and peer identities, with the peer as the channel conversation reference. A first inquiry creates the shared buyer/initial Opportunity. Exact reply references preserve that message's current Opportunity; a reordered reply remains durably reviewable until its parent arrives. Unquoted later messages require explicit association so unrelated orders cannot silently collapse into one need. The existing **Association review** flow can keep a message on a need, attach it across channels, or create a separate Opportunity. An unresolved reply to an as-yet-uncorrelated outbound message remains visible in capture receipts for review; #40 can correlate its authoritative outgoing receipt without inventing engagement.

The normal **Answer and qualify** command consumes these same persisted messages and approved Business context. It still requires accountable ownership/explicit handback and current AI/authority policy. Qualified requirements are ready for the configured conversion review; capture alone confirms no booking, quote or sale. A buyer's explicit request for a person pauses the associated Opportunity and supplies a visible next action. The inbox links to the configured approved escalation contact and existing takeover controls; escalation does not claim an external notification.

A valid text `smb_message_echoes`/`message_echoes` activity from the verified Business App number can take over an unambiguous associated Opportunity. It pauses queued work across channels through the existing control generation. Other Opportunities retain their state. An exact available reply reference selects its current purchasing need; otherwise the peer must have only one associated need. Ambiguous activity stays unassigned and blocks affected automation while an Owner/Admin selects an associated received message using **Associate activity and pause Opportunity**. It does not guess a purchasing need or permanently take over unrelated needs. An explicit subsequent handback permits future work; duplicate/reordered old events cannot reverse it. Status notifications are retained separately as provider observations for future #40 receipt correlation and are never classified as manual origin.

Unsupported message types/fields, unknown origin, inconsistent identities and unresolved reply visibility remain explicit gaps. Unfamiliar app-origin metadata cannot establish manual activity; a canonical provider-evidence fingerprint detects changes even to fields outside the supported text shape. Pending accepted activity blocks dispatch before worker processing. A known exact reply reference fences its purchasing need; an ambiguous peer-scoped event fences that peer's work. Known-peer coverage gaps use the same scope, including after private content expires. Unknown-scope events and conflicting provider identities conservatively block the affected connection. Provider status observations do not fence a purchasing need as manual activity. Original incoming records remain available. A visibility gap cannot be cleared by a customer claiming complete capture: fix support/configuration and establish fresh valid capture, or explicitly associate supported ambiguous activity. Reconnect/reselect creates a fresh authorized generation; no old unknown evidence becomes current proof. A current provider check reporting lost ownership, permission or number eligibility stops intake and recovery without hiding captured records.

## Private data and retention

`whatsapp_intake` records the selected connection generation, authorized actor, shared inbox connection, retention choice and capture evidence. `whatsapp_receipt` records scoped deduplication identity, normalized staging content, processing state, optional shared conversation/Opportunity association and expiry. Both have forced RLS, restricted column updates, composite Business foreign keys and schema/security reapplication checks. There are no generated migrations; the parent merger applies the reviewed schema with the existing `pnpm db-push` environment. No target database rollout is claimed here.

Recovery purges private staging content after the explicitly chosen retention period, including disconnected generations. The global cleanup function caps the supplied worker time at actual database time, so a future worker clock cannot erase unexpired staging across Businesses. Unprocessed expiry records a visibility gap. Minimal deduplication/message/status/association metadata and immutable peer/reply-reference scope remain; already captured inbox content follows the shared Business record policy. Agree the live inbox retention/export/deletion/cancellation policy and provider processing rights before activation. This feature does not invent a legal retention period or promise that staging expiry deletes the separate shared inbox record.
