# Saved discovery schedules and recovery

A saved search records the reviewed Discovery brief, approved provider policy and per-run allowance alongside an explicit IANA Business time zone, local time and weekdays. Saving or editing requires an Owner/Admin with current MFA and explicit recurring/public-query approval. Editing a paused search keeps it paused. Resume reauthorizes the saved brief under the current actor/session; changed targeting or provider policy requires an explicit edit and approval first.

Timing rules are explicit inputs: expired local days and overlapping scheduled runs are skipped, with visible reasons. Missed intervals are never backfilled. A late occurrence on its intended local day may still start. Temporal calendar arithmetic advances local dates, rather than adding 24 hours. Its `compatible` disambiguation selects the first repeated wall time and advances missing wall times by the DST gap. This also applies to non-hour transitions. The UI shows the next occurrence in the saved Business time zone. [Temporal time-zone semantics](https://tc39.es/proposal-temporal/docs/timezone.html).

## Durable ownership

PostgreSQL commits each scheduled occurrence, its next occurrence and the outbound dispatch records atomically under the Business lock. A unique occurrence index and the saved current due time prevent duplicate runs. Edits/pause/resume rotate the revision and dispatch capability; every delayed event is compared with stored state. The same checks guard queued runs and later provider reservations. A pause cannot retract an already accepted external request; its reservation and completed evidence remain accounted for.

Trigger.dev delayed tasks own persisted delivery, scheduled dispatch and worker recovery. Effect runs only inside an individual discovery attempt. The application starts no scheduling timer or cron process. A **Trigger-owned scheduled recovery task** drains pending transactional outbox records, including failures between database commit and Trigger acknowledgement. It is a recovery mechanism for persisted dispatch, not an in-process replacement scheduler. Its cadence is an explicit operator configuration. Failed dispatches remain visible; retry ordering favors records with fewer delivery attempts. [Trigger delayed triggering](https://trigger.dev/docs/triggering), [scheduled tasks](https://trigger.dev/docs/tasks/scheduled).

Trigger keys use global scope, so retries from different parent tasks resolve to the same task. Application idempotency remains authoritative beyond the provider key lifetime. Accepted but unacknowledged enqueue requests are safely retried. Delivery attempts do not authorize additional discovery spend. [Trigger idempotency](https://trigger.dev/docs/idempotency).

Worker infrastructure retries are bounded to three Trigger attempts. A retry of the same durable run may continue successful checkpoints within the original execution allowance and absolute deadline. Completed searches, reviews, prospect identities, observations and usage are reused. A failed, uncertain or outstanding provider reservation stops automatic recovery; it never issues that call again. Further provider attempts require the existing explicit #13 resume approval and consume the remaining allowance. After exhausted worker retries/cancellation, terminal hooks record safe stopped/paused reasons when persistence is reachable. A database outage that also prevents the terminal hook remains a Trigger operational failure requiring operator attention; no successful recovery is claimed. [Trigger retry lifecycle](https://trigger.dev/docs/errors-retrying).

## Access and isolation

Current actor membership/capability, persisted session/MFA, reviewed targeting, reach, provider policy and allowance are checked before dispatch and at attempt start/reservation, including recovery. The existing MFA policy has no background bypass: schedules stop with an access reason when their authorizer expires, signs out or loses access. Verify the authenticator and resume with the current session to reauthorize. This can stop recurring schedules after the policy's 12-hour Business assurance window; unattended long-lived service authorization is outside #14.

Both new tables use forced Business RLS and restricted grants. Transaction-local actor/Business context stays on the protected query connection; external Trigger/provider calls happen outside transactions. Narrow schema-owner functions expose only pending opaque dispatch capabilities and permit acknowledgement or terminalization after access revocation. They cannot read briefs/results, grant allowance or create research. Queue payloads are strictly validated identifiers; they cannot supply scope, budget, tool permissions or targeting instructions. Public views omit session IDs and dispatch/execution capabilities. Provider/task failures use allowlisted diagnostic messages.

## Activation and operation

The live discovery provider remains contract/configuration gated in `configuredDiscoveryProvider()`; #16 supplies that adapter. Deterministic application workflows do not need production credentials. No live provider, Trigger deployment or schedule attachment is claimed by this implementation.

To activate the worker adapter, configure `TRIGGER_PROJECT_REF`, `TRIGGER_SECRET_KEY` and an operator-selected `TRIGGER_DISCOVERY_RECOVERY_CRON` in the web/worker environments. Deploy the tasks, attach/verify that recovery cadence and the delayed discovery tasks, verify the restricted runtime database role and connectivity, then explicitly set `DISCOVERY_WORKER_DEPLOYMENT_CONFIRMED=true`. Environment values alone do not deploy or verify anything. SDK 4.8.3 is pinned; the adapter uses its supported delayed tasks, scheduled tasks, global idempotency and attempt metadata, with no reliance on newer scheduling-window features. Keep task payload/log access restricted to operators; payloads carry opaque execution capabilities.

Refresh Discovery to inspect **Dispatch pending**, **Scheduled**, **Paused**, run progress and safe failure reasons. Results and usage remain available after failure. For access expiry, verify in Security and resume. For changed policy, edit/review the current brief and allowance, save, then resume if paused. For a stopped run with uncertain usage, review the retained evidence and use its separate explicit recovery controls; resuming a schedule authorizes future occurrences and does not silently restart old stopped runs. Separately resuming an old run explicitly rebinds its unfinished checkpoints to the current active schedule revision; a later pause/edit still fences that queued execution.
