# Sender health and assisted recovery

Both approved email sequences and ordinary inquiry dispatch call the common current `identityView` readiness guard, including the native token-refresh confirmation. Health ingestion uses the same PostgreSQL Business advisory lock. A health failure committed before the final dispatch lock blocks transport. If dispatch already owns that lock, it can finish its bounded provider call first; an accepted or uncertain attempt cannot be undone. Repair never resets attempts, allowances, cancelled intents or unknown acceptance. Existing explicit sequence resume and inquiry review/handback remain necessary.

## Configure and review evidence

Provision only the `platform_operator.sender_health` capability through the schema-owner process. This capability participates in central privileged-role classification. Business admins cannot grant it. Every protected operator operation rechecks the actual session, current capability and authenticator verification younger than 15 minutes after acquiring the Business lock. Operators need no Business membership; their narrow sender setup read access and sanitized native grant metadata do not expose credential columns or inbox messages. Business members retain their normal scoped views; Salespersons can read and acknowledge their Business's alerts.

Use **Businesses → Review sender health alerts → Business ID → sender** (`/platform/sender-health`). The matching Business surface is **Sending identities → Review sender health**. Both audiences receive separately persisted, duplicate-safe **in-app** alerts atomically with an incident. They remain queryable after host/worker restart or a failed client response. No email, webhook delivery, subscription or external notification service is implied. Acknowledgement records team/operator receipt, never repair.

For each sender, configure a new attributed policy version with its actual source authority, HTTPS artifact origin, exact measured sender population, window length, reporting delay, freshness, source-artifact retention and per-metric thresholds. There are no production values or healthy toggles supplied by the application. The selected source route is authenticated **assisted review**: a current authorized operator reviews actual provider/recipient evidence, submits an artifact SHA-256 and credential-free reference, measured counts and the exact current Business/identity/version/connection/reply binding, native account subject and OAuth generation. The service derives the binding for the UI and rejects mismatched submissions. Source URLs are references only; the application never fetches them or accepts message bodies, credentials or arbitrary diagnostic payloads.

Metric definitions are fixed by this input contract:

| Metric                     | Failure numerator                                                                | Denominator                                              |
| -------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------- |
| SPF, DKIM, DMARC alignment | Messages failing the respective check in trusted receiver authentication results | Messages assessed using those trusted results            |
| Bounces                    | Definitive permanent delivery failures                                           | Provider-accepted submissions in the reviewed population |
| Complaints                 | Attributable recipient complaint reports                                         | Delivered messages in the reviewed population            |

These are reviewed population measurements, not a claim of universal recipient telemetry. An operator must establish the population, coverage, source access and trustworthy denominator before entering zero. No data, a provider acceptance, a Sent item, a timeout, a throttle or a 5xx cannot establish zero complaints, delivery, authentication success or a bounce. A source using a different definition (for example domain-wide Postmaster spam rate) cannot be relabelled into this contract. No domain-to-mailbox aggregate mapping is authorized by this implementation.

Each metric chooses **count** or **rate**, with an explicit minimum denominator; rates are fractions. Equality with the configured limit fails. Insufficient samples are unknown. Snapshots are never added as deltas, even under different report keys. Replaying a key and identical normalized payload returns its durable record; changed payload conflicts. Already-open failed conditions do not create another incident or alerts; append-only failure markers advance their repair window even when repeated failures no longer exceed a lowered current threshold. Event source ordering uses window end and observation time, with durable insertion order for equal timestamps. Older windows/observations cannot replace newer ones. Future observations, wrong window length, expired proof and reports exceeding the configured reporting delay are rejected. Freshness expires at equality. Policy changes and all exact bindings invalidate prior health proof.

To repair, explicitly select the incident(s) on **Record provider evidence or repair** and supply a newer complete window beginning at or after each failed window's end. Every metric needs a sufficient sample and must pass the current policy **and the original failed policy**. The population, source origin and window definition must remain comparable. Native sending-authorization failures additionally require the currently selected native account to be connected with actual sending permission. A generic connection refresh, changed setting, acknowledgement, lower threshold or unrelated positive report cannot clear an incident. Recheck overall sender readiness after recording repair, then use the existing explicit workflow review/resume controls. Unknown attempts remain evidence-only recovery work.

## Provider boundaries

Native Gmail and Microsoft grant/connection failures are ingested from the existing authenticated provider adapter path under the same lock, with exact current generation/account bindings and safe failure classes. They create `sending_authorization` incidents; they are never represented as SPF/DKIM/DMARC failure, bounce or complaint counts. A sending pause does not disable inbox processing, change selected scope/history, erase captured records or affect other senders. An actual revoked read grant can prevent new synchronization; retained correspondence remains accessible.

- Gmail API sending and reading permissions remain separate. Its HTTP success/acceptance does not establish delivery, and API quota/access errors are not complaint telemetry. See [Gmail errors](https://developers.google.com/workspace/gmail/api/guides/handle-errors).
- Gmail Postmaster is separately permissioned domain reporting. It can omit low-volume data, is delayed and measures particular recipient/authenticated populations. Its feedback loop needs controlled DKIM signing and a supported Feedback-ID; this transport does not promise that telemetry. **Consumer Gmail does not need control of gmail.com or Postmaster access**: an authorized assisted review may use actual exact-account receiver authentication results, delivery evidence and attributable recipient reports for its explicitly measured population. If the evidence is absent, show unknown and obtain it through assisted review. See [dashboards](https://support.google.com/mail/answer/14668346?hl=en) and [feedback-loop requirements](https://support.google.com/mail/answer/6254652).
- Microsoft `Mail.Send` does not grant read or administrative reporting. Graph sendMail `202` is processing acceptance. The current Graph v1.0 message trace API exists but requires separate `ExchangeMessageTrace.Read.All`, work/school access and tenant prerequisites; personal accounts are unsupported. It is not a complaint feed or all authentication results. This implementation adds no trace/admin scope or telemetry subscription. See [sendMail](https://learn.microsoft.com/en-us/graph/api/user-sendmail?view=graph-rest-1.0), [errors](https://learn.microsoft.com/en-us/graph/errors) and [message trace permissions](https://learn.microsoft.com/en-us/graph/api/messagetracingroot-list-messagetraces?view=graph-rest-1.0).

No Gmail/Graph health webhook is invented. No additional monitoring product is selected. Live provider approval, source access/coverage, customer authorization and actual reviewed threshold/retention inputs remain launch decisions, not deterministic implementation blockers.

## Persistence, diagnostics and retention

`sender_health_record` is a forced-RLS ledger with scoped identity FK, globally ordered positions, unique event keys/fingerprints and narrowly granted append operations. Policy/evidence/repair writes require operator authority; ordinary scoped dispatch can append native-failure incidents and the two audience alerts. Business read policies hide operator alerts. Immutable policy/incident/repair/alert/acknowledgement summaries preserve current dispatch safety and attribution. Diagnostics expose only the existing allowlisted error code and generated request ID, never raw provider payloads, artifact content or credentials.

**Remove expired source artifacts** invokes an operator-authorized, Business/identity-scoped maintenance command. Its fixed-search-path database function erases source-evidence entry payloads (references, artifact hashes, binding snapshots and measurements) older than the current configured retention. It retains an event-key/fingerprint tombstone for duplicate/conflict handling, and policy/incident/failure/repair/alert audit needed to enforce unresolved restrictions, including the original failure measurements, binding and latest failed window. A replay cannot restore erased evidence or make it current. This is explicit operator maintenance, with no hidden process timer. Settlement of longer-lived safety-audit/offboarding retention is part of live data policy; this command does not claim to delete inbox/history or provider-owned reports.

Schema changes use `pnpm db-push`, not migration files. Reconciliation reapplies the health FK, policies, forced RLS and narrow grants, and runtime verification rejects missing protections. The parent merger applies/verifies the actual target database using its existing environment; isolated PostgreSQL test execution does not establish target rollout.
