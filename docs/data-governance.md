# Business data export and connection offboarding

Issue #56 composes retained discovery/inbox records, #46 subscription cancellation, #48 immutable seller documents, native connection generations and private storage. `/businesses/{businessId}/data` is the Owner/Admin entry point. Current MFA, Business membership and an effective operator-approved policy are required. No new operator capability is introduced.

## Activation and policy

The operator supplies `BUSINESS_DATA_POLICY_JSON`, `BUSINESS_DATA_WORKER_DEPLOYMENT_CONFIRMED=true` and `TRIGGER_BUSINESS_DATA_CRON` to both web and Trigger. Deploy `maintain-business-data` before confirming it. Existing private R2/US/account fingerprint, cleanup schedule and Trigger configuration are still required. The policy storage scope must equal the fingerprint produced by the configured R2 adapter. There are no production legal or commercial defaults.

The strict schema is `src/models/data-governance.ts`. Supply:

- `id`, increasing `version`, exact authorized `businessIds`, `mode` (`test` or `live` in production composition), reviewer, supporting evidence and effective dates.
- Explicit Owner/Admin access, post-cancellation permission and financial preservation acknowledgements.
- `retention.retainedRecords = source_contract`, an explicit `financialEvidenceUntil` or null while review is outstanding, and its evidence. Original seller-document retention also protects referenced supporting files. Missing financial retention preserves bytes; it does not invent an unlimited access period.
- Export lifetime, single-use grant lifetime, per-source row bound, total byte bound and exact storage fingerprint. Technical schema bounds are not legal retention periods.
- Per-source adapter identity, original executed scope reference, reviewed source origins, evidence and explicit export/post-cancellation rights. Exa additionally requires the current validated executed-order activation from ADR 0009/#2; a live API key is unnecessary for retained export. Public self-serve terms or a customer assertion do not substitute for the executed rights. The original discovery run's export and cancellation permissions must agree.
- `deletion`: null when unapproved, otherwise an explicit general-file permission, earliest disposal date, exact file holds and evidence. Updating a recorded policy requires a new version. There is no production policy editor granting a Business authority to approve its own legal terms.
- Explicit native revocation permission and bounded retry count/delay. Provider-specific activation/credential vaults remain independent.

The public policy view excludes the configured Business ID list, storage fingerprint and private native envelopes. Policy ID/version contents cannot be rebound through a new request. Missing, withdrawn, expired, wrong-mode or wrong-storage policy blocks affected production commands. General-file deletion requires its own confirmation. Retained domain-record destruction is not automatically authorized by connection offboarding: this workflow preserves source-permitted discovery, conversations and immutable domain history; a different approved domain disposition must be reviewed separately.

## Export and download

POST `/api/businesses/{businessId}/data` accepts `{ command: "export", input: { requestKey, part } }`. Part defaults to 1; later numbered parts retrieve the next bounded primary-source rows. The manifest includes part number, offsets, row bound and `hasMore`, so the bound cannot permanently hide later records. Derived prospect/source roots follow the included relations. Each part is a current authorized view: new arrivals can change later offsets; parts are not a cross-part database snapshot. Each persisted request binds its original part and receiving actor; retries cannot change the part or take another actor's export. The application reads an explicit bounded source/column allowlist under restricted PostgreSQL and forced Business RLS. It never serializes arbitrary tables or provider events.

The JSON package includes Business profile, permitted prospect identities, repeated observations and legacy run results with original run/prospect relations, source policy snapshots, buyers/conversations/messages/Opportunity associations, versioned call notes, charge-specific paid periods, original invoice/credit snapshots, billing/tax snapshots and private-file metadata. Every represented source has exact included IDs, total/included/omitted counts and a SHA-256 over its exported records. The manifest supplies relations, format/policy versions, retrieval/source provenance, redaction and coverage limits. Run execution/callback secrets are omitted. Rights-denied or bounded-out records remain explicit omissions. Canonical JSON preserves formula-like source text without spreadsheet evaluation.

#49 financial cases use its existing authorized customer projection. Canonical financial effects preserve actual cash, native source/payment/invoice/period identities, original tax/allocation, linked credit and separately approved credit basis/residual. Cash and document rounding can differ; a residual is not classified as a fee, tax or FX. Both financial sources participate in bounded parts and exact coverage hashes. A narrow helper requires the exact pending actor-bound persisted export, current Owner/Admin membership and effective financial-preserving policy against database time. Operator evidence, native receipts/commands, leases/capabilities and raw actor/device/auth references are omitted.

Available seller invoices and credit notes are retrieved through #48's real current authorized grant/download path. Up to 10 attachment reads and the total package byte bound apply. Included bytes must match the original immutable size/hash and are stored as base64. Missing, unsafe or bounded-out attachments have a per-document reason and retain their original hash/ID; separate authorized document downloads remain available. Raw private file bytes are outside this bundle and use their own current file access. Credentials, encrypted native envelopes, auth/invitation links, URL query/fragment capabilities, worker/recovery keys and unrelated operator/global authentication records are excluded. The manifest explicitly says **partial customer export, not infrastructure backup**. #58 owns infrastructure recovery.

The actual private artifact key is `business-exports/{businessId}/{exportId}.json`. The existing R2 adapter performs bounded private PUT/GET/DELETE. It is separate from `seller-documents/` and `business-files/`. The request freezes its package size/hash before conditional PUT. Lost acknowledgements and concurrent precondition conflicts reconcile only the same private object, original actor/Business identity, size and hash. An existing package cannot be overwritten or rebound. After PUT/GET the application reauthenticates and rechecks current role/policy before publishing ready state. The persisted policy window is checked against database time before and after storage I/O, including when the application clock is stale. Expiring actor-bound grants are hashed, single-use and checked against trusted database time. POST `.../data/{exportId}/access` creates a grant; POST `.../content` sends `{ token }` in the body, keeping it out of URLs/referrers. After GET, the receiver, Business, policy, expiry, immutable hash/metadata and current artifact state are checked again before bytes leave the application. Responses use private/no-store, nosniff and attachment headers.

Expired/abandoned artifacts have bounded exact-key cleanup leases and retry counters. Original approved artifact lifetime supplies this narrow disposal authority even after the receiver leaves. A caller's future application clock cannot expire a still-valid package in PostgreSQL. Deletion failure or lost acknowledgement leaves a recorded incomplete/deleting outcome; a later bounded delete is idempotent. Exhaustion remains visible and requires operator investigation.

## Approved offboarding

`command: "offboard"` requires a stable request key, the displayed policy ID/version, `confirmStop: true`, explicit general-file choice and either null cancellation or an explicitly confirmed original subscription action/request key. The immutable request commits its original actor, input and policy.

Within that same transaction, narrow definer logic:

1. Stops pending/running discovery and pauses schedules with new execution/dispatch/revision identities. Current acquisition checks reject start/resume and recurring reauthorization while stopped, including when a previous run would otherwise update an existing row. Old queued work cannot reach provider I/O or publish new dispatch capabilities.
2. Disables inbox connections and mailbox processing, changes mailbox policy versions, blocks pending sync and consumes/wipes old OAuth PKCE material. Saved sender connection, reply-route and identity versions also change and remain disabled after reopening; old sender observations and campaign approvals cannot authorize their new versions. Setup/native-grant writes remain blocked while stopped, including late callbacks that try to restore a quarantined credential.
3. Hands Opportunities to human control with new control versions, cancels pending ordinary actions and first-contact sequence work, and changes sequence generations/keys. Already committed/unknown provider acceptance stays available for reconciliation; it is never relabelled unsent.
4. Disconnects native grants and increments their generation/version before any slow provider request. The original encrypted revocation material moves to a private cleanup envelope unavailable to ordinary runtime SELECTs or customer exports.
5. Captures only exact eligible general-file IDs under the approved storage account. Billing files, supporting evidence referenced by billing/tax/seller snapshots and current legal holds are protected. No broad prefix or bucket deletion exists.

Native revocation follows on the scheduled worker using original persisted authority, trusted DB leases and bounded attempts. Before each effect, the worker checks the exact persisted target, original policy, storage identity, current holds/sharing, lease and policy window against database time. Meta checks again after its preparatory subscription read and Google before each token revoke. A prior batch claim cannot authorize an expired later effect. Exact expired-artifact cleanup retains its separate original lifetime authority after disclosure policy withdrawal. Generic file cleanup checks its original operation/storage identity and current protection before each delete; its lease expiry also uses database time. It never impersonates an expired purchaser/session. Disclosure still requires the current receiver. Requests for another Business or stale lease cannot select arbitrary cleanup targets. Replay/takeover/native action tombstones remain immutable. Pending remote identity cleanup blocks another Google/Meta grant from accepting the same remote identity; reconnect cannot race revocation.

Provider outcomes are deliberately specific:

- **Google Gmail/calendar:** official token revocation POST for the original attributed primary credential. A current active grant for the same subject in any other Business, or a new accepted grant in the same Business, prevents global/project-scope revocation. Rejected callback tokens have no verified stored subject and can belong to a different account: cleanup never posts those tokens to project-wide revocation. Their presence keeps the broader result manual/incomplete while private local copies are wiped. Local unlink and token clearing remain separate. A 200 is accepted revocation of the attempted original token; an invalid token after lost acknowledgement does not prove consent removal and remains incomplete after bounded retries.
- **Microsoft delegated mail/calendar:** local generation fencing and token clearing are implemented. No app-scoped delegated consent-revocation API is invented. The customer removes app consent using the appropriate provider-account/admin workflow. `revokeSignInSessions` invalidates unrelated application sessions and is not called.
- **Meta:** checks the saved exact provider/app identity and WABA, reads subscriptions, then removes our app's WABA subscription with the supported DELETE. Missing acknowledgement is reconciled by reading subscription membership on retry. Incomplete/paginated evidence stays unresolved. A shared WABA is not unsubscribed. `subscription_removed` is distinct from full consent removal and remains visibly incomplete for the broader offboarding task. Customer WABA/number/payment account deletion, deregistration, global token revocation and transfer are not performed.

Token copies are cleared after confirmed/manual/shared outcomes or exhausted attempts. Expired final worker leases also create an accountable incomplete tombstone and clear the token copy. Original approved retry-count/delay plus the bounded lease define a token revocation window; expiry clears private copies even if the current deployment policy is missing or withdrawn. This narrow hygiene authority cannot delete underlying domain data. File cleanup observes the original disposal date and holds against trusted database time. Current compatible configured policy must exactly match the original approved plan for destructive domain cleanup; changing/withdrawing it blocks that work. A new policy/version and new explicit scope are needed to change an approved plan. Existing issuer retention and approved financial-evidence dates keep required supporting files available under their current file authority, without changing original financial facts.

`command: "recordEvidence"` records a scoped Owner/Admin report and supporting record reference for externally removed consent or reviewed/transferred customer number control. Reports are attributed append-only history, never fabricated native confirmation or automatic transfer. Secret/private links are not accepted as evidence references. `command: "reopen"` separately permits new setup only when native cleanup is no longer pending. It does not reactivate old connections, OAuth callbacks, jobs, sender/sequence approvals or transferred control. A superseded stop request cannot act as a new approval after reopening; the UI generates a new request identity. Reconnect and authorize new work explicitly.

## Cancellation and preservation

When selected and confirmed, the web command composes #46's existing cancellation command **after local fencing**. #46 owns actual lifecycle policy, provider binding, request/confirmation/effective date and recovery. Only its exact action/request fields cross that seam. A missing billing policy can leave local offboarding stopped while cancellation remains incomplete; inspect Subscription payments and retry/reconcile its saved intent. The data plan's selected cancellation flag is not a native cancellation result. Offboarding does not refund a charge, manufacture a paid/grace period or delete financial history.

Operations #55 history/diagnostic retention grants no underlying deletion, financial or native-provider authority. Global users/sessions, multi-Business membership and #59 authentication/invitation/transactional delivery records are outside this Business cleanup and customer export. Their independent global or Business notification history and payload-retention authority remain unchanged. A real public auth/invitation regression verifies that stopped-Business offboarding preserves global and another Business's notification facts without exporting their IDs or private capabilities.

## Database and rollout

Five new tables: immutable `business_data_request`, mutable artifact-only `business_data_export`, hashed single-use `business_data_grant`, private helper-owned `business_data_step` and append-only `business_data_event`. No existing financial/domain rows are backfilled or deleted during schema application. Scoped FKs participate in prepare/drop/reapply reconciliation while the corresponding runtime table/column/helper write authority is paused. Security setup restores forced RLS, original policies, narrow owner-only helper paths, triggers, scope FKs and grants. Required SELECT and INSERT grants are checked separately. Fourteen operational definer helpers (including three pre-effect lease guards) have fixed empty search paths, no PUBLIC execution, restricted execution and non-owner runtime. Startup also rejects PostgreSQL's implicit default PUBLIC execution when an ACL is absent. Five private trigger functions have no runtime or PUBLIC execution. The runtime cannot select cleanup secret envelopes or directly change steps/events.

The parent/independent merger owns actual target `pnpm db-push`, the full sequential reapplication and independent before/after data/security verification. Child tests use disposable real PostgreSQL only. UI, live account/legal/provider setup, real R2 lifecycle protection and customer acceptance remain manual gates. Both Apple design skills are applied to source/flow; browser rendering and CSS/contrast/keyboard/zoom/preference measurements are not claimed.
