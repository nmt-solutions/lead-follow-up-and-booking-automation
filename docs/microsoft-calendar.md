# Microsoft Calendar appointment connection

Business Owners/Admins connect under **Business → Booking calendar connection** with verified MFA. Connecting, choosing a calendar, reconnecting and disconnecting require verification within 15 minutes. Reads use the normal Business session lifetime and recheck current roles/session after provider work. Calendar authorization is independent of sign-in and mail readiness. RFQ capture needs no calendar.

## Operator setup and supported accounts

Use a dedicated confidential **Web** app registration in the Microsoft global cloud, supporting **accounts in any organizational directory and personal Microsoft accounts**. Register the exact `{BETTER_AUTH_URL}/api/businesses/{businessId}/calendar/microsoft/callback` for each connecting Business; wildcards and SPA redirects are not supported. Configure the real publisher, account audience, client credential, user/admin consent policies and any required organization approval. This integration adds no SSO plugin or scheduling subscription.

Set server-only `MICROSOFT_CALENDAR_CLIENT_ID`, `MICROSOFT_CALENDAR_CLIENT_SECRET`, `MICROSOFT_CALENDAR_TOKEN_KEY_ID`, and `MICROSOFT_CALENDAR_TOKEN_KEYS` (JSON mapping key IDs to random 32-byte lowercase hexadecimal keys). Retain old keys until encrypted states expire and credentials have rotated. Set `MICROSOFT_CALENDAR_APPROVED=true` only after the actual app/account approvals and deployment setup are complete. All values and the canonical HTTPS `BETTER_AUTH_URL` are required; localhost HTTP is allowed for development. Missing setup stays unavailable. No placeholder secrets activate production.

Requested delegated scopes: `openid email profile offline_access User.Read Calendars.ReadWrite`. Calendar read/write is required for creation, event-read reconciliation and availability; `User.Read` binds calendar ownership to the authenticated Graph profile. No mail, shared-calendar, application, directory-administration or revocation-administration scope is requested. `offline_access` requests refresh tokens. Tenant consent policy can still require an administrator. Separate client registration prevents calendar lifecycle from sharing a login/mail client grant.

Account class comes from a signature/issuer/audience/expiry/nonce-validated ID token and its tenant ID, never an email suffix or browser input. The consumer tenant selects personal Outlook; workforce tenants select work/school. Known guest/substituted identities are refused. Only the global Microsoft identity/Graph endpoints are used. Unsupported guests, national clouds, group/resource/shared/delegated calendars and read-only calendars are unavailable. A mailbox absent from Exchange/Outlook cannot become ready just because identity consent succeeded.

| Account                                                                | Calendar                             | Availability                                                                                                          |
| ---------------------------------------------------------------------- | ------------------------------------ | --------------------------------------------------------------------------------------------------------------------- |
| Work/school with Exchange calendar                                     | Owned, editable primary only         | `POST /me/calendar/getSchedule`, selected owner's SMTP schedule                                                       |
| Personal Outlook                                                       | Owned, editable primary or secondary | Selected calendar's `calendarView`, including every relevant page, expanded occurrences/exceptions and all-day events |
| Work secondary, shared/delegated/group/resource, unsupported ownership | Unavailable                          | No fallback or guessed capability                                                                                     |

Selection revalidates owner address against the Graph profile, edit/share/private-item capability and primary identity where required. Reconnect retains the original signed subject/tenant; disconnect before switching accounts. Graph ownership aliases that cannot be matched remain unavailable. Availability treats tentative, busy, out-of-office, working-elsewhere and unknown as blocked; free/cancelled events do not block. Truncated, cyclic, malformed or untrusted paging fails closed. Personal accounts **never call `getSchedule`**.

## Persistence and booking recovery

Access/refresh tokens and PKCE verifiers use the shared AES-256-GCM primitive with Microsoft/Business/connection-specific authenticated context. State is hashed, single-use, ten-minute limited and actor/session/Business/generation bound. PKCE S256, nonce and confidential code exchange are wired to the application. Current integration roles and MFA, forced RLS, restricted column grants and composite Business/connection FKs apply. Public views and diagnostics never include credentials, codes or provider payloads.

The Business transaction lock serializes refresh, selection, booking and disconnect. This is the existing reviewed booking exception for bounded provider I/O. Refresh rotation replaces the stored token and re-encrypts with the active key; revoked/insufficient grants disable operations and ask for reconnect. Old Microsoft refresh tokens are not automatically invalidated by rotation, so delete them from local storage. Key loss requires restoration; it does not bypass encryption.

Appointments use #23's persisted intent, holds, current #19 takeover/policy/session guards and immutable history. Graph events have no attendees, online meeting or reminder. UTC payloads come from explicit app time-zone/DST conversion; response reads request UTC and immutable IDs. Invalid response times are refused. Customer communication remains a separate action.

A stable `transactionId` is supplied at creation for Microsoft's deduplication semantics. There is **no transaction-ID lookup endpoint or assumed transaction-ID filter**. Read-only recovery filters the documented named single-value extended property containing the complete Business/connection/calendar/opportunity/appointment/intent provenance, then reads the matching event through the selected calendar path and validates identity, metadata, revision and times. Multiple matches, changed metadata or external buffered conflicts remain unconfirmed/actionable. Event confirmation is retained only after the authoritative identity is durably stored.

Creation is never blindly retried after timeout, malformed success, 409 or lost database commit. A missing result is not definitive absence; keep the request unresolved for review/reconciliation. Conditional deletion first validates the unchanged event, its revision, provenance and empty attendees. A timeout or lost commit after deletion can remain unresolved when Graph has no retained event/tombstone; do not invent proof of cancellation or send/recreate automatically. Rate limits require waiting before an explicit read/reconciliation; no adapter mutation retry runs. The app cannot provide a global atomic lock against external calendar writers.

## Disconnect and provider-side revocation

**Disconnect deletes this app's stored credentials and disables local booking. It does not revoke Microsoft consent everywhere.** Pending callbacks are invalidated. Existing events/history remain. Rejected OAuth credentials are discarded locally, not falsely marked remotely revoked.

For personal accounts remove this app at [Microsoft account permissions](https://account.live.com/consent/Manage). For work/school use [My Apps](https://myapplications.microsoft.com/) → app → manage/revoke permissions; admin-consented permissions need the tenant administrator. Other sessions, grants or already issued access tokens may remain valid until expiry. We request no broad Graph revocation/admin scope and do not call sign-out as proof of consent removal.

## Controlled human live check (not executed by automated tests)

1. Operator records the actual registration/audience/tenant approval, exact Business callback and secret-store setup. Use a dedicated non-customer test Business and separate work/school test mailbox; its primary calendar must contain no customer events. For personal Outlook use a dedicated owned test secondary calendar. Do not test against a customer's primary calendar.
2. Owner verifies MFA, connects, grants only the listed scopes and selects the supported calendar. Expect account-specific availability, truthful setup/consent failures, excluded shared/work secondary calendars, and no mailbox-readiness change. Record sanitized account class/calendar choice and request IDs, never tokens/codes.
3. Configure explicit hours, time zone, duration and buffers in Appointments. Add bounded test busy/free/all-day/recurring events, including an exception; check slots across a DST boundary. Work uses primary free/busy; personal reads the selected calendar's expanded/paged view. Record expected versus actual instants.
4. In one dedicated test Opportunity explicitly request/book one future test slot, with **no customer attendees or invitations**. Expect one immutable event and a retained confirmed appointment; replay must produce no duplicate. Change/create an overlapping test event and reconcile: expect an actionable conflict. Remove only the test conflict and reconcile again. Any intentional transport fault injection must be controlled and bounded; after uncertain acceptance reconcile, never press a new-create workaround.
5. Cancel the unchanged test appointment; expect conditional deletion and retained cancellation evidence. Test denied consent, permission loss, reconnect and local disconnect. Expect local operations blocked and history retained; separately remove Microsoft consent using the appropriate account/admin steps. Record the separate revocation outcome without claiming immediate token invalidation.
6. Remove remaining explicitly identified test events only, revoke the test app grant and remove test deployment secrets when finished. Record sanitized evidence, cleanup results and UI acceptance on #25. This procedure is authorization for a human-controlled check, not a claim that live OAuth/bookings were run by the agent.
