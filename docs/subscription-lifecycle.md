# Subscription renewal recovery and cancellation

The existing payment application, HTTP composition and `reconcile-subscription-payments` Trigger task now reconcile the subscription lifecycle alongside immutable captured periods. Native Razorpay cards use the actual subscription, invoice and payment APIs. A signed receipt requests reconciliation; authorization, subscription activation, a card-update callback and a browser return never establish payment or access.

## Reviewed configuration

The deployment operator supplies `SUBSCRIPTION_LIFECYCLE_POLICY` to **both web and Trigger**. Its exact schema is `lifecyclePolicySchema` in `src/models/subscription-lifecycle.ts`. Deployment configuration is the authorization boundary, as for the existing Razorpay account review; Businesses cannot approve their own policy. No new operator capability is introduced. The existing reconciliation capability already participates in central privileged-role classification and requires fresh operator MFA.

All fields are required. Supply actual reviewed terms and retained evidence, rather than copying synthetic test values:

- `id`, positive `version`, native `mode` (`test` or `live`), `reviewedBy`, `checkedAt`, `effectiveFrom`, `effectiveUntil`, and nonempty `evidence` references.
- `graceSeconds`: the expressly reviewed number of seconds, including explicit zero where applicable. `graceAccess` is either `none` or `remaining_allowance`. The latter retains only unused units from the last captured period; it creates no paid period, new allowance, recurring charge or paid-through extension.
- `cancellationTiming`: `immediate` or `cycle_end`, sent exactly to the native cancellation API. `cancellationAccess`: `paid_through` or `provider_end`. The former honors eligible captured periods; the latter also caps access at the confirmed provider end. A scheduled cycle-end cancellation excludes periods starting at/after that end. Captures after a confirmed end remain financial evidence without reviving cancelled access.
- `preserveRecords: true`: expiry/cancellation fences acquisition and automated dispatch while retaining incoming inquiries, engaged conversations, stored results and human work. This configuration performs no deletion or offboarding.

Missing, invalid, wrong-mode, future or expired policy blocks grace and customer cancellation. It does not suppress reconciliation of genuine captured payments, erase financial history, or extend the existing paid-through boundary. Fix the actual reviewed deployment configuration and run the same recovery task; there is no fixture-only production bypass. Reusing an observed policy ID/version with different contents conflicts. A new reviewed version is a new attributable policy snapshot; earlier ledger entries remain immutable.

## Application and native contracts

Owners/Admins use `workspace`, `refresh`, `updatePayment` and `cancel` on `createSubscriptionPaymentApplication`. Business scope and current membership are checked in restricted transactions. New commands accept only `{ actionId, requestKey }`; no amount, card, period, provider URL or Business identity comes from their bodies. Authorization repeats after external reads, and before native cancellation POST. A separately provisioned reconciliation operator can inspect the existing queue and refresh authoritative status with fresh MFA; there is no manual paid override.

- `POST .../subscription-payments/update-payment` returns validated native Standard Checkout input: the actual public key, persisted/bound native subscription ID, `subscription_card_change: true`, and the exact `https://checkout.razorpay.com/v1/checkout.js` script. Only active/pending/halted native subscriptions support this action. It does not create another subscription or invent a recovery URL. All card details stay with Razorpay. Callback data is discarded and only requests server reconciliation; no callback signature or token is accepted as payment authority. Account evidence must continue to establish card-only settings, including disabled UPI/eMandate.
- `POST .../subscription-payments/cancel` commits an attributed intent before I/O, then uses `POST /v1/subscriptions/:id/cancel` with the reviewed `cancel_at_cycle_end` boolean. The native resource is fetched and bound by account/mode, immutable operation/financial notes, subscription, plan, quantity, cycle count and saved customer before the command. Immediate confirmation requires native cancelled status and `ended_at`; cycle-end acknowledgement must retain the observed exact `current_end`. Generic scheduled-change flags are not cancellation proof.
- A timeout, crash, denied final authority check or lost acknowledgement leaves **requested/unconfirmed** cancellation. Repeated requests/restarts never POST cancellation again. Recovery only reads the same native resource. A terminal native status with its authoritative end can confirm the original request. If a scheduled acknowledgement is lost and native reads cannot establish its purpose, the intent remains visibly unresolved until terminal evidence; investigate the exact saved subscription with the provider rather than blindly repeating the operation. No cancel/resume/plan-change API is fabricated.
- An authoritative terminal end earlier than an acknowledged future cancellation tightens that end without extending it or rewriting a captured period. `provider_end` access follows the earlier end; `paid_through` may still retain the eligible paid period. Cancellation notices do not claim access ended while that paid-through access remains active.
- Native polling returns a validated `LifecycleObservation` independently of per-charge `PaymentObservation`s. Pending/halted failure evidence must concern the unpaid boundary (`current_end` or an exactly bound issued invoice's `billing_start`) rather than a previously recovered cycle. Terminal observations never restart; a later same-terminal response can fill a previously missing end time.
- Existing raw HMAC-SHA256 verification, retained secrets, native event identity, account/mode binding and payload hash remain. Normalized signed lifecycle receipts additionally retain the exact native event name, optional subscription status and native event timestamp. Wrong saved subscription references remain unmatched, without manufactured Business ownership. Receipts never apply the hinted state directly: reordered/duplicate failure or activation events only cause authoritative polling.

Provider retries remain provider-owned. The app does not manually charge invoices, synthesize a hosted link, or promise that halted arrears are automatically collected. The supported customer action is the documented card-change Checkout; only the resulting independently reconciled captured invoice can restore its eligible period. Domestic manual invoice charging is not enabled.

## Persistence, entitlement and notification seams

`subscription_payment.lifecycle` persists pending/active/past_due/cancelled state, access state, paid-through, failure boundary, grace end, reviewed policy, bound provider observation, and requested/confirmed cancellation with request actor/time and effective end. `subscription_lifecycle_event` is its append-only attributed ledger. Stable action/key uniqueness deduplicates state checkpoints and command notices; financial snapshots, charges, periods, usage, seller invoices and credit notes are not rewritten.

`current_paid_scope` is the existing central operational reader. It now applies exact grace and cancellation boundaries to the real period and its remaining units. Discovery workspace/admission/run reservations, saved schedules, campaign reach, sequence reservation/final dispatch, ordinary inquiry dispatch and native Meta sending already compose this reader. The payment workspace uses the same reader. Clock boundaries are evaluated on every admission/dispatch; stale UI state does not extend access. Recovery does not requeue or reset old cancelled/blocked tasks or prior period reservations.

State transitions and commands persist actual customer-facing notices with `channel: in_app`, `status: available`, stable source ID, Business/action, attribution and timestamp. Both customer and operator views render them. This states availability in the app, not that a customer read the notice or that an email was sent/delivered. `notificationFeed` is an operator-authorized public application query for #59 to compose platform delivery using the stable source IDs. #59 must record its own channel, recipients and provider acceptance/delivery evidence; it must not reinterpret in-app availability as email delivery.

Dependent contracts:

- **#47:** use the lifecycle/current scope and original `subscription_period.snapshot`/`charge` contracts. Confirmed cancellation fences future changes; an unresolved cancellation is not a reversible cancellation or a safe new mandate. Plan changes/proration and supersession require their own approved command and captured-payment binding.
- **#49:** a cancellation is not a refund. Canonical per-charge payment/invoice/order/period/tax identities remain available; any reversal or post-cancellation capture correction needs an attributable new adjustment rather than changing issued history.
- **#56:** tax/financial reporting reads frozen charge-specific snapshots, including original agreed renewal basis and actual approved charge tax. Lifecycle grace creates no sale, payment, seller invoice or fresh allowance.

The new table participates in Drizzle's table filter and managed prepare/secure scoped-FK reconciliation while financial writes are paused. Runtime has SELECT and INSERT separately, forced Business RLS, no history mutation and only the action lifecycle column update grant. Startup verifies those rights independently, its scoped FK and policies. No new security-definer function, deletion helper, bearer capability or expiry/retention clock is introduced. Parent/merger must apply/reapply ROOT's actual target schema before deploying; implementer verification uses disposable restricted PostgreSQL only.

## Primary provider evidence checked 2026-11-07

Razorpay documents pending/halted failure behavior, Standard Checkout's card-change parameter and exact script, hosted failure links, and the domestic manual-charge restriction in [Payment Retries](https://razorpay.com/docs/payments/subscriptions/payment-retries). The app uses the documented Checkout input and independently reconciles captures; it does not claim to have sent Razorpay's email or observed its delivery.

[Cancel a Subscription](https://razorpay.com/docs/api/payments/subscriptions/cancel-subscription) specifies the native POST/boolean, cycle-end timing, terminal status/end fields and the inability to restart a cancelled subscription. [Subscription States](https://razorpay.com/docs/payments/subscriptions/states) distinguishes authorization/active/pending/halted/terminal states. These provider states do not replace the app's paid-access authority.

Existing [native integration evidence](razorpay-card-billing.md) retains capture/invoice/calendar/account/signature sources. Actual merchant activation, account method settings, card/network/currency behavior, native schedule/cancel/card-update behavior, reviewed commercial/legal policy, live credentials, webhook deployment and Trigger cadence still require authorized performed sandbox/account validation. No live charge, cancellation, customer email, browser/UI test or human acceptance is claimed.
