# Isolated infrastructure recovery

Recovery creates a **private inspection environment**, not a production cutover. The web application records accountable intent and safe history; a separate Trigger project owns administrative recovery. Normal web and sales workers keep pooled `app_runtime` connections. They must never receive the direct owner URLs, backup key or recovery storage credentials.

The normal runtime verifier rejects any database containing the owner-created `recovery_quarantine` schema. The target runtime also defaults to read-only transactions. A restored session, invitation, job, OAuth token, callback, sender approval or native idempotency record cannot authorize resumed effects. Unknown post-cutoff outcomes stay unresolved. There is no automatic production activation or customer backup-download endpoint.

## Review before a request

Provision `platform_operator.recovery` through trusted administration; it defaults false and participates in central privileged-role/MFA classification. Every request, resume, stage claim, result and inspection requires current recovery authority and platform MFA. A request UUID binds its original actor and the complete server-selected plan. A fresh session can renew that same actor's worker delegation without replacing the original request or backup.

`src/models/infrastructure-recovery.ts` defines the strict approved plan. Supply actual reviewed RPO/RTO objectives, backup/file retention, observation expiry and byte limits. These values have no product, legal or provider-plan defaults. Freeze an immutable review ID, exact Business, native backup ID/hash/cutoff, reviewed schema hash and all source/target identities. `RECOVERY_APPROVED_PLANS_HASH` authenticates the exact server registry text; an HTTP caller can select only a plan UUID and request UUID.

Source and target projects, branches, hosts, buckets, worker, auth and webhook identities must differ. The target is explicitly disposable and identified as recovery. Separate retained-copy storage must differ from both active buckets. The approved inventory binds the configuration fingerprint and its expiry, deliberate Vercel deployment, dedicated recovery worker deployment, private US R2 storage and actual commercial/isolation review evidence. Merely supplying credentials does not verify deployment.

`pnpm recovery:bundle` computes the immutable bundle from the installed source-owned schema, security, runtime/repository and configured Drizzle tooling. Any changed bundle requires renewed review; a caller cannot supply SQL, a command, executable path or callback through the API. No generated migrations or destructive reset of populated application data is used.

Configuration is distinct from a deployed observation. - Neon is selected as `aws-us-east-1` (Northern Virginia). Before target operations, fixed-host authenticated GETs verify both exact projects and their branch read-write endpoint hosts/regions. Runtime uses the pooled restricted SQL-created role; backup/migration/recovery uses separately held direct administration. Console/API-created Neon roles inherit powerful `neon_superuser` membership and are unsuitable as `app_runtime`. [Regions](https://neon.com/docs/introduction/regions), [project API](https://neon.com/docs/reference/api/projects/get-project), [branch endpoint API](https://neon.com/docs/reference/api/branches/list-project-branch-endpoints), [role privileges](https://neon.com/docs/manage/roles).
- Recovery tasks deploy with `trigger.recovery.config.ts`, whose directory is separate from normal tasks. Use a separate project/environment, API key and worker deployment. Web enqueue uses scoped `auth.withAuth`, explicitly requests `us-east-1` and passes only the operation UUID. The worker compares actual project/environment/deployment and `ctx.run.region` with the approved inventory; absent or different native observations block administrative work. Select the same region for scheduled recovery in the project Regions page. A run's region does not establish payload/log storage residency. There is no invented region property in `trigger.config.ts`. [Trigger options](https://trigger.dev/docs/triggering#region), [configuration](https://trigger.dev/docs/config/config-file), [context](https://trigger.dev/docs/context).
- Private R2 uses the US jurisdiction endpoint. An eastern location hint is best effort and is not Virginia placement. Actual retained copies are required; a database restore cannot recreate deleted bytes. R2 does not provide S3 bucket versioning compatibility, so this workflow promises no automatic version history. [Data location](https://developers.cloudflare.com/r2/reference/data-location/), [S3 compatibility](https://developers.cloudflare.com/r2/api/s3/api/).

## Backup and disposable target preparation

Owner tooling runs only in a private approved recovery environment. It reads process configuration, never a customer-supplied connection or an application's `.env` file. Supply compatible native PostgreSQL `pg_dump`/`pg_restore` executables; the embedded test server package does not include them. [PostgreSQL Windows tools](https://www.postgresql.org/download/windows/), [pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html), [pg_restore](https://www.postgresql.org/docs/17/app-pgrestore.html).

1. Approve a backup template and inventory with actual source/target identities, byte limits and the current schema bundle. In the private owner environment, set `RECOVERY_PLAN_ID`, separately held source direct administration, source pooled runtime, a private archive directory, an independent 32-byte base64 backup key and the native tool paths.
2. Run `pnpm recovery:backup`. One exported repeatable-read PostgreSQL snapshot supplies the native custom-format archive, actual cutoff, complete table contents/count digests, schema-definition digest and representative Business record IDs/hashes. The archive is AES-256-GCM encrypted with the manifest as authenticated data, written once under an immutable ID and given a whole-artifact SHA-256. Plaintext exists only in an isolated temporary directory and is removed after the process. Private archive storage/access and key escrow remain operator responsibilities.
3. Review the emitted backup ID/hash, actual cutoff and selected retained file manifest; freeze the resulting registry and its hash before an application request. A backup template or successful export is not restore evidence. Infrastructure archives retain original protected financial/native/operator/auth state and are intentionally separate from #56's redacted paginated customer packages. The native archive includes the public application schema across Businesses; it is never exposed to a Business. Restricted inspection is fixed to the selected Business.
4. Provision a separate empty disposable Neon database and SQL-created restricted runtime role/login with independently selected credentials. Verify separate projects/branches/hosts, bucket, worker, auth and webhook identities. Set the target's pooled runtime/direct administration and an independent target seal in the owner environment, then run `pnpm recovery:provision-target`. Native identity checks precede this action. The tool refuses populated targets; dropping the initially empty public schema uses no CASCADE. The private quarantine marker and read-only runtime are installed first. No source database is reset and no cloud resources are provisioned by this tool.
5. Deploy the dedicated recovery worker with only its approved registry/inventory, source and target credentials, private archive/key and retained/target R2 credentials. `RECOVERY_RETAINED_OBJECTS` maps the selected opaque file IDs to their original object keys, content types and immutable Business/file/owner/hash metadata. Only reviewed hashes/byte sizes are copied, into the isolated target bucket with create-only writes. Retries verify existing target bytes rather than overwrite them. Missing retained bytes become explicit omissions.

Native logical export/restore uses direct connections and `--no-owner --no-acl`; privileges are independently reapplied from reviewed source. Neon's native PITR is a separate provider operation: it has actual history-window and root-branch restrictions and can overwrite every database on a branch. This application does not invoke it against production or assume a commercial history window. [Neon native export](https://github.com/neondatabase/website/blob/main/content/docs/guides/export-neon-postgres-compatible.md), [instant restore](https://neon.com/docs/postgres/backup-restore/branch-restore).

## Operation and recovery evidence

From Businesses, an authorized operator opens Infrastructure recovery, reviews the frozen cutoff/objectives/coverage and confirms the selected plan. Trigger executes these distinct stages:

1. Requested intent and original actor/request binding.
2. Actual disposable target identity and empty-target verification.
3. Native schema/data restore in one transaction; exact complete inventory reconciles a lost commit acknowledgement before any repeat restore.
4. Full reviewed prepare/Drizzle/schema/security application; independent restricted-runtime/RLS/grant/helper verification.
5. Actual target application record IDs/hashes and safe record projections queried through the nonowner runtime against the physically distinct backing store.
6. Verified retained object bytes or explicit omissions, with external work quarantined.
7. Original native financial outcome polling through existing financial application boundaries, requiring their independent domain authority. No mutation or fresh payment/message key is issued. Other stale or unavailable control-plane outcomes remain unresolved.
8. Private inspection readiness. This is not production activation, restored customer authorization or permission to resume queued effects.

The source journal freezes each plan, cutoff and bundle, retains attempted/ambiguous/completed stages, records trusted database times and current MFA attribution, and uses database-owned expiring leases. Refresh and resume keep the same operation. A fresh explicit delegation is required when its original session no longer has current assurance. A queue outage, started restore or created target cannot establish verified recovery.

Both snapshot cutoff and observed request-to-verification time are shown; they are drill observations rather than RPO/RTO guarantees. Current health includes missing/stale environment evidence, native region mismatches, unverified deployment and outstanding authorization/retention/commercial setup. Preserve current native outcomes, stop/offboarding generations, revocations and expired private payloads independently of rollback. Before any future production cutover, reconcile all relevant original domain outcomes and provision fresh current auth/MFA/membership/credentials/callback/worker/sender approvals; unavailable evidence keeps the environment private.

## Cost reconciliation

Selected commitments, backup/storage/recovery usage, observed requests and billed charges have stable evidence identities and original currencies. Explicit actual/estimated/unpriced classifications remain distinct. Missing prices stay unpriced. Reconcile selected evidence through the existing #54 cost application; independent current `costs.manage` authority is required in addition to recovery authority. Exact replay does not append another cost. A shared commitment uses its shared identity rather than being repeated per recovery or Business; customer-paid Meta charges are excluded.

## Local proof and manual acceptance

Set `RECOVERY_TEST_PG_BIN` to an installed compatible native PostgreSQL tool directory (or make the tools available on PATH), then run the affected `tests/*recovery*.test.ts` files with pnpm/Vitest. Tests start separate genuine source/target PostgreSQL clusters with restricted runtime roles. Public source fixtures create retained prospects/evidence/conversations, genuine native payment/invoice/refund/credit/receipt history and queued work. A backup preceding a later accepted native refund is actually restored; source-domain reconciliation identifies the original native outcome and restored execution cannot repeat it. File copies and omissions are byte-hash checked. Full managed reapplication, current/foreign/MFA authority, default ACL/grant negatives, substituted identities, stale evidence and failed/lost-acknowledgement restart are separately exercised.

These tests do not perform cloud provisioning, production restore, deployment, browser validation or real provider/customer actions. Actual account approvals, commercial plans, provider credentials, source/target network controls, retained copies/key escrow, deployed worker/schedule and configured isolated drill remain launch gates. The user validates rendering, keyboard/focus, compact/wide layouts, 200% text, appearances/preferences and the confirmation/error/MFA/retry/history flows. Never add `tested` from automated evidence.
