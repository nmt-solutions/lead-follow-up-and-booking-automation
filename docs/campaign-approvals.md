# First-outreach approval contract

`src/application/campaigns.ts` owns authenticated draft, review, decision and inspection commands. `src/application/campaign-policy.ts` owns campaign selection, version/replay and approval policy, evaluated against facts loaded under the repository's Business lock. Sales staff can prepare versions; a current Business Owner with the existing MFA-backed session requirements records approval or rejection. The API and Business campaign page use this application boundary. Manual drafts require no AI credentials.

Each append-only revision binds the exact Business-scoped prospect/contact identities, addresses, evidence and uncertainty, sender identity and connection/reply-route versions, email subjects/bodies, relative delays, attempt cap and mandatory stops. Equal addresses cannot appear twice in a version. Each configured message has one authorized attempt; the cap includes the initial message and equals the number of configured messages. The initial delay is zero; each follow-up delay is a positive whole number of minutes after the previous successful attempt. There are no product timing, recipient-quota or pricing defaults.

Saves use an actor-bound request key and expected version. Decisions bind the revision ID and canonical snapshot hash. Identical retries preserve the original attribution; conflicting retries and stale versions fail. A later version supersedes the old plan for current use without removing its approval history. New discoveries and changed contact evidence stay outside prior snapshots.

`review` accepts a revision/hash, exact prospect/contact/address and step index. It works before approval and returns the immutable content, current checks, and a persisted evaluation through the shared email eligibility service. Purpose is derived from the step: initial contact is `sales_outreach`, subsequent steps are `sales_follow_up`. Recipient permission can bind to a scoped discovered prospect without creating an Opportunity. Existing Opportunity permissions keep their scope. Content reviews remain separate from campaign approval; a one-click-unsubscribe checkbox cannot establish transport capability.

`inspect` is the consumption interface for #34. It accepts the same exact reference and requires a recorded approval. Its result includes historical approval, the immutable revision, the selected recipient/step, current authorizing Owner/session and commercial-policy version, evidence, sender, reach, conversation/control checks and dated eligibility. Blocked current checks remain visible alongside historical approval. Existing direct engagement stops first outreach and directs the user to the inbox; this does not merge buyer identities or hand back an Opportunity.

Inspection is not an execution grant. Its transaction lock has ended when the result returns. #34 must establish persisted action identity and scheduling/attempt accounting, re-evaluate all current gates under the Business and policy locks immediately before an effect, honor eligibility time boundaries and reply/control/opt-out stops, and reconcile ambiguous delivery. Custom stop text requires explicit execution handling; it cannot weaken mandatory stops. #35/#36 own sending adapters. This ticket supplies no queue, worker, provider call, launch command or campaign-send record; execution is always reported as unconfigured and not scheduled.

Both campaign tables have forced RLS and restricted SELECT/INSERT runtime grants; revisions and decisions have no runtime UPDATE/DELETE grant. Schema push and the security reconciliation step preserve their history and policy expressions. The real-persistence campaign tests exercise reload, concurrent edits/decision retries, scope, role/MFA/session revocation, changed sender/evidence, permission/suppression, validation and zero outbound effects. UI validation remains user-owned.

Own-client initial-email preparation and evidence are implemented separately in [Email handoffs](email-handoffs.md). Its locked preparation guard is not a transport or follow-up execution grant.
