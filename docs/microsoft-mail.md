# Selected Microsoft mailbox synchronization and sending (#30, #36)

Read this contract before changing Microsoft mail consent, delta recovery or production activation. The shared [mailbox contract](mailbox-processing.md) governs actor/Business scope, history bounds, inbox association and current-state dispatch controls. Mail uses conventional TypeScript; Trigger.dev owns durable continuation.

## Activation and account support

Production is off by default. Implementation uses deterministic HTTP/account fixtures, actual isolated PostgreSQL and a controlled clock. No private live mailbox, consent flow, send, invitation, provider revocation or worker activation is part of automated verification.

1. Register an application-owned confidential **web** OAuth client in the global Microsoft cloud. To offer both supported classes, its account audience must support organizational and personal Microsoft accounts. Register the exact HTTPS callback for each assisted pilot: `/api/businesses/<Business UUID>/mailboxes/<mailbox UUID>/microsoft/callback` under `BETTER_AUTH_URL`. Saving a mailbox does not register its callback with Microsoft. Localhost HTTP is available for controlled development. [Authorization-code flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow).
2. Record publisher/application verification, privacy/data-use review, applicable security assessment or Microsoft 365 certification obligations, tenant consent approval, account coverage and their actual costs. Microsoft requirements are distinct from Gmail restricted-scope assessment; this implementation claims no universal Microsoft assessment fee or completed approval. Delegated `Mail.Read` is available for personal and work/school accounts, but tenant consent policy can still require administrator approval. The current Microsoft-managed recommended policy restricts ordinary user consent for mail permissions. An app-registration checkbox does not override that policy. [Permission reference](https://learn.microsoft.com/en-us/graph/permissions-reference#mailread), [current tenant consent policy](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-app-consent-policies).
3. Validate the intended account and mailbox before launch. Supported contract classes are the signed-in user's primary Outlook.com mailbox and a member user's provisioned Exchange Online primary mailbox, in the global cloud. Signed issuer/audience/nonce/expiry, stable subject/tenant, matching primary address, work-account `userType=Member`, mailbox `userPurpose=user` and usable mail access are checked. Shared/delegated, guest, linked/resource, secondary, alias-as-owner, in-place archive and sovereign-cloud combinations are unavailable. A normal Archive **folder inside the primary mailbox** is different from an in-place archive mailbox. Do not infer support from a display name, a Microsoft login or Calendar access. [User purpose](https://learn.microsoft.com/en-us/graph/api/resources/mailboxsettings?view=graph-rest-1.0), [reachable users/clouds](https://learn.microsoft.com/en-us/graph/users-you-can-reach).
4. Confirm Exchange Online licence/service-plan and provisioning requirements for each work/school pilot; personal Outlook accounts follow their own service availability. Missing/inactive/on-premises mailboxes remain unavailable. The older mail overview still mentions hybrid access, but Microsoft's specific deprecation notice says hybrid REST access ended in July 2023; this implementation follows the latter. Record mailbox licence costs, app review/setup/maintenance and incremental database/HTTP/Trigger costs alongside the [operating-cost baseline](operating-costs.md). No broker, IMAP, directory-wide or application-permission fallback is selected. [Hybrid deprecation](https://learn.microsoft.com/en-us/graph/hybrid-rest-support).
5. Supply server-only `MICROSOFT_MAIL_CLIENT_ID`, `MICROSOFT_MAIL_CLIENT_SECRET`, `MICROSOFT_MAIL_TOKEN_KEY_ID` and `MICROSOFT_MAIL_TOKEN_KEYS` through the deployment secret store. The keys value maps key IDs to 64 hex characters; use a fresh random 256-bit active key and retain older keys while their ciphertext exists. Set `MICROSOFT_MAIL_OAUTH_APPROVED=true` and `MICROSOFT_MAIL_PRODUCTION_PREREQUISITES_CONFIRMED=true` only after the above evidence is recorded. `MICROSOFT_MAIL_CLOUD` defaults to `global`; any other value disables composition. Calendar and login settings never activate mail.
6. Separately deploy `synchronize-selected-mailbox` and `poll-selected-mailbox` with the same restricted database connection, mail configuration and encryption keys as the web host. Set `MAILBOX_WORKER_DEPLOYMENT_CONFIRMED=true` only after deployment verification, with the existing Trigger project/secret configuration. The legacy `poll-selected-gmail` task forwards already queued work to the common continuation. This issue does not activate those workers.

## OAuth, refresh and disconnect

An MFA-verified Business Owner/Admin first saves the immutable Microsoft mailbox identity and processing selection. OAuth requests `openid email profile offline_access User.Read MailboxSettings.Read`, plus `Mail.Read` only when reading is requested and `Mail.Send` only when sending is requested. MailboxSettings.Read validates mailbox class; Mail.ReadBasic cannot read the selected bodies. Sending requests, effective grants, processing consent and Calendar/login remain independent. Extra returned permissions do not authorize processing. Missing send consent can leave valid requested reading usable. Native sending is described below; saving requests or connecting never sends.

State is hashed, single-use, ten-minute, PKCE-protected and bound to Business, mailbox, policy version, grant generation, actor and exact authenticated session. The stored state hash supplies the independent OIDC nonce check. Tokens and verifiers use the existing AES-256-GCM vault with Microsoft-mail/Business/mailbox-specific authenticated context. Code exchange and Graph I/O occur outside tenant transactions. A callback cannot substitute the selected address, original subject or tenant. Unaccepted credentials are discarded. Scope changes, disconnect, changed membership/MFA and another refresh fence stale network completions before storage or ingestion.

Refresh rotates encrypted access/refresh credentials under a compare-and-swap and rechecks the stable Graph mailbox-owner ID as well as the primary address; an unchanged display address cannot substitute another owner. Microsoft may invalidate refresh access after user/admin action or policy changes; reconnect is explicit. Replacing a refresh token does not itself revoke the old provider token, so local storage replaces and forgets it securely. [Refresh lifecycle](https://learn.microsoft.com/en-us/entra/identity-platform/refresh-tokens).

Disconnect immediately increments the generation, removes locally stored tokens, clears effective local grants, invalidates reply readiness and pauses affected follow-ups. Captured correspondence remains readable. **It does not prove Microsoft-side consent removal.** The UI links personal account permissions and work/school My Apps; a tenant administrator must remove tenant-granted consent. Removing provider consent may affect other integrations sharing that app registration. No `revokeSignInSessions`, directory grants or tenant-wide consent-removal operation is requested. [User/admin consent management](https://learn.microsoft.com/en-us/entra/identity/enterprise-apps/manage-consent-requests).

## Selected content and stable identity

Browse mailbox folders after authorization to obtain canonical IDs; the catalog reads folder metadata only. Select exact folders (each subfolder separately), exact conversation IDs, or supported sales mail across the primary mailbox. Catalogs and per-folder cursor collections are bounded to 50 folders; oversized/unverified configurations remain unavailable. A selected folder ID is verified against `/me`; its display label is not authority.

Metadata is validated before any body request. New folder-selected inquiries must be addressed to the authenticated primary address and match an Owner/Admin-supplied subject phrase. Exact selected conversations and previously captured conversations supply explicit sales context. Whole-mailbox mode handles established conversations only. Unknown or unrelated mail, drafts, outbox, junk/deleted mail, mailing lists and declared automatic messages do not authorize body reads. This conservative classifier can miss legitimate subjects/languages: explicitly select the relevant conversation to authorize it. Mail text is untrusted content, rendered as text, and cannot change authority, recipients, tools or budgets.

Each selected message is fetched individually using `Prefer: IdType="ImmutableId"` and `outlook.body-content-type="text"`. IDs remain case-sensitive and stable across moves inside the same primary mailbox; archive/export/reimport can change identity. The current folder metadata observation updates separately from the retained original message. Exact typed sender/recipient data, bounded headers/RFC references, times and text body are checked again against listed metadata. Attachments, MIME expansion and HTML execution are absent. [Immutable IDs](https://learn.microsoft.com/en-us/graph/outlook-immutable-id), [message fields](https://learn.microsoft.com/en-us/graph/api/resources/message?view=graph-rest-1.0), [body preference](https://learn.microsoft.com/en-us/graph/api/message-get?view=graph-rest-1.0).

Supported outgoing observations require a message currently in this owner's Sent Items, matching primary From/Sender and an external recipient. Manual-reply takeover additionally requires an exact RFC In-Reply-To and resolved Opportunity; standalone initial messages remain for explicit [handoff review](email-handoffs.md). Inbox-only selection does not observe Sent Items. A selected conversation still filters individual timestamps and folders before bodies; it never broadens into whole-conversation bodies. Moved sent mail, other aliases/delegates, activity outside the approved selection, or an unsupported header/body cannot establish complete manual visibility. A Sent Items observation is evidence of supported mailbox activity, not proof a person clicked Send or proof of delivery.

The internal `createMailboxSendRecorder` seam persists actual app transport receipts, scoped to a retained received message in the same Business/mailbox. No public sync/event endpoint accepts app-origin claims or receipts. Matching recorded sends are excluded before bodies and cannot trigger takeover; subsequent buyer references follow their receipt to the received message's **current** Opportunity association. Recorded receipts are separate from the native pending-identity path below. Received/manual RFC chains use the common inbox and #19 control transaction. Replays, reorder and retries do not repeat inbox records, cancellation or takeover after handback. Unmatched selected replies remain visible for review; they do not invent a buyer or Opportunity. An incoming reply observed before its referenced Sent Items page is retained outside Opportunity association, then reconciled when that exact source becomes observable. It cannot fall back to a different conversation-default need. The legacy physical `gmail_manual_message` table stores these common native observations by immutable mailbox ID; original content/history is retained separately from subsequent folder observations. Pending observations respect the latest observed folders and current approved time scope before reconciliation.

## Delta state, recovery and visibility

Graph deltas are **per folder**, not Gmail history IDs or watch tokens. Private persisted cursors bind each folder's opaque next/delta link to the Business/mailbox, selection/query version, mode and approved time bounds. The exact legacy #30 metadata field list is also accepted on saved opaque delta links; individual messages are always fetched with the current Reply-To-aware selection. Each URL is confined to the exact global Graph `/v1.0/me/mailFolders/<canonical ID>/messages[/delta]` collection. Cross-owner, cross-folder, arbitrary-host, body-selection and expansion links are rejected before a bearer is forwarded. Redirects, network time, response size, collections and text sizes are bounded.

Incremental baseline/delta scans enumerate selected-folder **metadata** without the received-date delta filter, avoiding Microsoft's documented filtered-result limit. The shared application independently enforces the saved new-mail boundary before any body fetch. History remains off by default. Explicit history uses a separate folder list query with inclusive start, exclusive end and the appropriate received/sent time, one message per page and one persisted total selected-message allowance. Retry/resume cannot reset that allowance. No attachment or old body is imported just to establish a delta baseline. [Folder delta contract](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0).

Every page atomically commits inbox effects and its cursor/checkpoint under current Business/session/MFA, policy, connection, generation and permission-observation checks. An unfinished or stale page advances nothing. Overlapping/replayed pages and moves cannot duplicate records. HTTP 429 records a safe retry time and the worker durably defers the same job; application retries make no Graph call before that time. Failed response payloads, tokens and opaque cursor URLs are absent from public errors/diagnostics. [Throttling guidance](https://learn.microsoft.com/en-us/graph/throttling).

Expired delta/continuation state restarts metadata enumeration only in the current approved selection, with the original body time/count bounds and deduplication. Removed/missing messages and cursor gaps leave a retained **limited** visibility state after available mail is recovered: deleted mail cannot be reconstructed. Recovery does not claim a complete historical import. A manager can review the gap and explicitly disable reading/save, then re-enable/save to authorize a new boundary. Prior correspondence remains available. [Delta reset/replay semantics](https://learn.microsoft.com/en-us/graph/delta-query-overview).

Trigger owns delayed 60-second polling and retries; there is no process timer or public Graph notification endpoint. A successor job is stored atomically, so enqueue loss and duplicate poll delivery reuse the same successor. Current session/team authority is required on every continuation. Initial/recovery scans pause affected work. Explicit completed-baseline evidence distinguishes next links from completed rounds: every initial page remains recovering until all folders finish. A healthy multi-folder round retains its previous fresh visibility while paging and refreshes freshness only when every folder finishes. Visibility expires after five minutes without a complete current round. Limited states keep polling available mail while affected follow-ups remain paused.

No subscription is created or represented as active. Graph subscriptions expire and lifecycle events require reauthorization, recreation and delta recovery; an endpoint challenge alone would not authenticate notification data. A future notification path must validate stored subscription/resource/tenant/client-state binding before enqueue and must not use a hint to authorize arbitrary mailbox/Business reads. The current path recovers stopped polling and expired delta gaps using durable saved work. [Subscription overview](https://learn.microsoft.com/en-us/graph/change-notifications-overview), [lifecycle gaps](https://learn.microsoft.com/en-us/graph/change-notifications-lifecycle-events).

Incoming replies cancel stale unanswered work at #19's concrete dispatch fence, including another channel of the same Opportunity. Supported manual replies pause that Opportunity until explicit handback; independent needs keep their work. Permission/visibility failures also invalidate #27 readiness and pause affected work while retaining incoming history. Native Microsoft currently attests scoped visibility, **not complete general reply-route capture**, so it cannot independently make #27's general two-way sender route ready. Neither reconnect nor restored visibility revives canceled work or silently hands human ownership back. Sequence execution uses #34 with the native transport below.

## Native approved dispatch (#36)

Both ordinary grounded inquiry replies and approved outreach sequences use the selected Business's actual Microsoft primary mailbox. Web and Trigger composition simultaneously support Gmail and Microsoft. Sender checks resolve by the exact connection provider; sequence allowance is explicitly bound to one adapter or an operator-reviewed list sharing the same reservation cap, and each committed attempt retains its adapter and connection. Recovery uses that persisted binding even if current allowance settings change. There is no catch-and-retry through another provider, fixture, transactional mail or alias.

The chosen path uses delegated **Mail.Send** for direct MIME `sendMail` and `reply`, with the existing separately requested read/processing permissions for current reply visibility. It does not request `Mail.ReadWrite`. Draft/createReply then send could provide a stable draft/native identifier, but draft creation requires write permission and introduces a separate mutation/crash lifecycle. Selecting that alternative would need new explicit product configuration/consent; this implementation never expands scopes silently. Each HTTP operation is bounded and has no internal transport retry.

The public dispatch command commits one immutable intent before transport, then rechecks Business/actor/session/MFA, ownership/handback, commercial authority, approved knowledge/profile, eligibility/suppression, sender identity/health, selected reply visibility and (for sequences) approved recipients/timing/cap/reach/allowance. Credential decryption/refresh happens invocation-locally inside the reviewed shared Business dispatch lock. It never calls the Microsoft connection service's separately transactional `credential` method. Current scopes, stable owner ID, primary address, work-account member capability and primary user-mailbox purpose are checked; all application guards repeat immediately before transport after preflight/refresh.

For an ordinary reply, the exact current selected parent is read again (immutable native ID, RFC ID, conversation, original From/Sender, recipients, Reply-To, subject and text). MIME reply uses the original sender per the provider contract. Different/multiple Reply-To targets, changed parent content, unsupported address normalization or unapproved recipient expansion block transport; the app does not silently redirect a reviewed reply. Sequence follow-ups use direct `sendMail` with the previous reconciled RFC reference and exact approved recipient, avoiding reply-to-self on a Sent message. The application does not promise that Graph will assign a particular conversation ID.

An empty **202 Accepted** is persisted as `accepted_pending_identity` with the accepted processing time and submitted correlation, without a fabricated native message/conversation ID. Ordinary action state is dispatched with native identity pending. Sequence state remains committed with the explicit `provider_accepted_identity_pending` reason; no next step is scheduled until exact current Sent evidence resolves identity. The original processing acceptance remains separately retained when Sent reconciliation later establishes native identity. A positive 202 remains processing acceptance even with unexpected non-identity response text; a malformed non-202 success does not establish the documented send result. Neither state establishes delivery.

Lost responses, malformed successful responses, 5xx and result-persistence failures retain the original commitment and never authorize blind resend. Native 401/403/capability failures feed #37's persistent sending-authorization incidents and repair requirements; refresh or reconnect alone cannot repair them. Sending-only rejection can preserve separately valid reading. A definitive 429 respects Retry-After; only an explicit non-acceptance permits another sequence reservation subject to the existing cap/allowance/current guards. Ordinary replies remain single-attempt and require a fresh review/evaluation after definitive cancellation.

Reconciliation sends nothing. It uses unique exact currently authorized observations from the selected canonical Sent Items folder and current OAuth/sync generation, exact sender/recipient/Reply-To, body/subject, parent references and bounded occurrence time. Duplicate identities, different content/participants/parent, moved mail, stale/removed selection, revoked grants or missing evidence stay unresolved. Current source provenance is distinct from the original provider response. App-origin exclusion needs the whole exact committed effect, not a marker/header. A changed manual Outlook reply follows the current Opportunity association and triggers takeover; a buyer reply can follow an exact committed RFC reference before Sent sync, without creating engagement or delivery claims.

The outgoing RFC Message-ID is **correlation only**, never a deduplication guarantee. The provider documentation does not establish that caller RFC identity or every body/header/subject survives normalization. Deterministic fixtures explicitly model both retained exact evidence and mismatched/unresolved evidence. Live personal and work/school acceptance must verify those behaviors, Sent-copy delays, UTF-8 content/subject/Reply-To and reply recipient/thread behavior. If exact identity is unavailable, processing acceptance remains positive and correlation remains unresolved; the UI explains that the action will not resend.

To enable these registered sequence/inquiry flows, explicitly select mailbox processing (history may remain off) and complete current sync; this authorizes bodies only for established selected sales threads and exact registered outgoing/reply references. No complete general reply capture is claimed. Inbox-only, selected Sent-only or incomplete thread/folder selections cannot make the native dispatch route ready. Current attributable sender health from the operator's persistent #37 evidence route, customer policy/eligibility and actual configured allowance remain necessary. No new billing, DNS, provider trace/admin permissions or production health defaults are supplied.
