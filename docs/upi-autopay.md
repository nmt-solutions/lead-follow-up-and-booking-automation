# Separate UPI AutoPay agreements

UPI remains disabled in the initial cards-only configuration. Issue #61 adds an optional, independently reviewed UPI merchant path to the existing reach-change application. It does not enable UPI on the card merchant. Existing card settings still require `card=true`, `upi=false`, `emandate=false`; the optional UPI merchant requires `card=false`, `upi=true`, `emandate=false`. An unavailable configuration leaves cards unchanged and displays an actionable setup message.

## Provider contracts and supported scope

Primary Razorpay documentation rechecked on 2026-11-07:

- [Supported payment methods](https://razorpay.com/docs/payments/subscriptions/supported-payment-methods) and [Subscriptions settings](https://razorpay.com/docs/payments/subscriptions/settings): method availability is controlled for the merchant account. UPI recurring payments use INR.
- [Subscriptions FAQ](https://razorpay.com/docs/payments/subscriptions/faqs): UPI subscription updates and additional charges are unsupported. Customers can pause/cancel using their UPI app; a customer pause cannot be silently undone by the merchant. Published limits vary by account, merchant category, use case and supported PSP/app. This implementation assigns no universal UPI ceiling.
- [Create subscription](https://razorpay.com/docs/api/payments/subscriptions/create-subscription): plan, quantity, total count, start and notes are documented inputs. No invented `payment_method` creation parameter is sent.
- [Integration and signature verification](https://razorpay.com/docs/payments/subscriptions/integration-guide): Standard Checkout proof uses HMAC-SHA256 of payment ID and the **server-saved** subscription ID. A callback or UPI PIN does not establish a paid term.
- [Cancel subscription](https://razorpay.com/docs/api/payments/subscriptions/cancel-subscription): the original collector is cancelled at the approved cycle boundary before a new collector is created. A lost response remains unresolved until independently corroborated; pending/unknown cancellation is never treated as a stop.
- [Orders](https://razorpay.com/docs/api/orders/create), [payment entity](https://razorpay.com/docs/api/payments/entity) and [fetch invoice](https://razorpay.com/docs/api/payments/invoices/fetch-with-id): an approved one-time order funds the prorated reach difference. The future mandate separately funds each exactly matched monthly invoice. Native fees/base money are retained only when actually returned; they do not establish bank settlement.

Using a distinct merchant account is an **application isolation strategy**, inferred from account-level method settings. It is conditional on the operator obtaining actual provider approval for the proposed merchant/account arrangement. It is not a claim that Razorpay entitles every merchant to another account. Unsupported arrangements remain unavailable. The implemented path supports explicitly reviewed INR, UTC calendar-month plans, one quantity and exact configured minimum/maximum amounts, MCC, apps and VPA handles. UPI never selects the international-card PATCH/proration path or subscription add-ons. A supported separate order is a separate customer-approved payment, not an unspecified subscription additional charge.

## Configuration and evidence

Server-only inputs, deployed consistently to web and Trigger:

| Input                                                            | Meaning                                                                                                                                             |
| ---------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------- |
| `RAZORPAY_UPI_ACCOUNT_REVIEW`                                    | Full versioned `razorpayAccountReviewSchema`, with a distinct account and `upiPath` from `src/models/upi-autopay.ts`.                               |
| `RAZORPAY_UPI_KEY_ID`, `RAZORPAY_UPI_KEY_SECRET`                 | Credentials belonging to that exact merchant/mode. Key prefix must match the reviewed mode.                                                         |
| `RAZORPAY_UPI_WEBHOOK_SECRETS`                                   | JSON array of 1–3 exact UPI merchant webhook signing secrets.                                                                                       |
| `RAZORPAY_UPI_SANDBOX_KEY_ID`, `RAZORPAY_UPI_SANDBOX_KEY_SECRET` | Read-only use of actual test-mode resources for a `native_sandbox` evidence record. No experiment is created automatically.                         |
| `FINANCIAL_UPI_ADJUSTMENT_POLICY`                                | Independently reviewed refund/dispute/access policy for the original UPI account/mode. Does not inherit reconciliation, documents or tax authority. |
| `SUBSCRIPTION_REACH_POLICY`, `SUBSCRIPTION_LIFECYCLE_POLICY`     | Existing independently reviewed commercial/proration/stop and lifecycle policies. No operating defaults are seeded.                                 |

`upiPath` records an explicit path ID, enabled state, MCC, INR/method/monthly schedule, minimum/maximum in minor units, supported apps/handles, account-support references, terms and explicit identity mappings. Each mapping binds one app Business plus its original account/customer to the distinct UPI merchant customer. Native customer IDs are merchant-local: neither browser prefill nor the old card customer ID establishes the new identity. A native customer read verifies the configured ID before effects; final authorization checks its actual UPI method/customer/handle and subscription binding.

Sandbox records distinguish `deterministic_fixture` from `native_sandbox`. Fixtures are accepted only in test mode and never count as provider validation. Live creation requires actual native sandbox evidence and read credentials. The verifier reads the known test subscription, plan, failed authorization, successful authorization, initial captured payment, renewal captured payment and their two paid invoices. It checks the merchant credential path, customer/method/handle/INR, exact unrefunded amounts, invoice/payment/order/subscription/plan relationships, quantity-one plan lines, consecutive monthly boundaries and final native cancellation. A missing, contradictory or unavailable read blocks validation. The demonstrated amount also bounds new recurring amounts. No live sandbox work is performed by configuration loading or these tests.

Keep account support, sandbox provenance and controlled evidence references separate from the in-app validation. An enabled flag alone is insufficient. Never put secrets in evidence or terms. A particular unsupported amount/app/MCC/identity arrangement needs a new actual review, not a global readiness override.

The Subscriptions method toggles, merchant category, PSP/app limits, customer-to-Business mapping and relationship between test credentials and the declared merchant remain attributed deployment review inputs. The native `/methods` read corroborates general merchant method availability; it does not independently prove the Dashboard's Subscriptions toggles or account approval. Isolating a UPI merchant is an application strategy conditional on provider approval, not a promised provider feature. Native sandbox verification corroborates the listed test resources and quantity-one billing, including consistent authorization refund state; deterministic HTTP fixtures are a separate evidence kind and cannot establish performed sandbox or live validation.

## Customer and operator workflow

1. The Owner/Admin chooses a trusted target quote and **UPI AutoPay** in Reach changes. The server freezes quote, taxes, amount, currency, plan/count, effective/renewal dates, commercial terms, original and new native account/mode/customer, method, path and explicit app identity mapping. Original card actions, periods and document sources stay immutable.
2. A platform reconciliation operator with current MFA chooses **Validate exact UPI agreement**. Native account methods, customer, plan and any required sandbox resources are read. A locked, private immutable validation records the actual operator/session/factor and exact snapshot. The customer cannot self-authorize this review.
3. The customer reviews and approves those exact frozen terms under current membership/session/MFA. A new reviewer uses a new UUID and creates a new validation; the customer must approve again. Previous reviewer UUIDs cannot be adopted. Setup changes require fresh agreement review; they never rewrite prior capture, invoice or renewal terms.
4. Each mutation attempt commits before I/O. The original card collector is scheduled to stop at the approved paid-term boundary using its original credentials. Only a verified successful native acknowledgement or a correctly matched cancelled subscription proves that boundary. Unknown old cancellation cannot create a new collector. The future UPI subscription starts at that exact boundary.
5. Standard Checkout authorizes the **new** UPI customer. `/api/businesses/:businessId/subscription-payments/confirm-mandate` persists the proof intent UUID/actor/payload before signature/native reads. It verifies using the frozen UPI account secret and saved subscription. Authorization records a reconciliation hint and grants no paid period. Failed/lost authorization recovers the original intent; it never repeats a mandate or charge POST.
6. An expansion then offers its approved one-time order. Actual matched UPI capture, account/mode/customer, order, exact gross/tax/currency and period bindings are necessary before one idempotent paid adjustment applies reach. A card/foreign/mismatched actual capture remains an attributed financial review fact and grants nothing. Renewal requires its own captured payment and fully matched paid native invoice. No overlap exception allows both recurring collectors to fund the same effective term.
7. Customers can pause/cancel through their supported UPI app. Reconciliation displays actual native lifecycle state. The app cannot resume a customer pause or use card-update UI for a UPI mandate. Independently approved native cancellation still uses the original account even when new UPI creation is disabled. Late actual money remains in history without undoing cancellation or Business offboarding stops.

`/api/webhooks/razorpay-upi` and `/api/webhooks/razorpay-upi-adjustments` select a fixed server account/key ring. They validate raw bytes and original source account/mode; body `account_id` or a client selector is never sufficient. Event identities include original account and mode. Financial reads, refunds, disputes, cancellation and recovery resolve the original frozen account; missing retained credentials fail safely rather than using the current default card singleton.

## Persistence, recovery and checks

No tables, columns, constraints or raw writable financial ledgers are added. Exact UPI agreements, immutable attempts, private validations, checkout-proof identities, captures and cancellation history use the existing scoped payment/reach/lifecycle ledgers and their required managed uniqueness/FKs. New `upi_review_current` is a scoped operational boolean helper; `protect_upi_reach_event` is a private insert-trigger function with no runtime/PUBLIC execution. Both have empty search paths and explicit ACLs. Managed prepare atomically pauses reach table/helper access until full schema/secure reapplication. Runtime startup checks include both helpers and the trigger binding.

The validation's trusted database lease is capped by the operator's remaining MFA lifetime. Missing or null UPI agreement data cannot disguise an UPI merchant snapshot as a legacy card event. Checkout intents retain the original actor, UUID, complete signed payload and hash before native reads. Recovery verifies that retained proof with the original account and server-saved subscription, records only authenticated reconciliation hints and performs no new native mutation. Private signatures are omitted from public payment history and customer packages; original archive/restore history remains intact.

The source-owned #58 bundle includes the new adapter/models/application/helper code. Native physical recovery and reviewed schema repair retain original UPI mappings, account/method/money, proof replay identity, private approval history and #52 private filing history. Restored queues remain quarantined. Inspection and domain operations use independent **current source** authority; restored grants and capabilities do not activate collection. A snapshot cannot undo later native cancellation.

Automated verification uses public commands/queries/events, real PostgreSQL under a non-owner runtime, deterministic external HTTP through `configuredPayments`/`configuredFinancialAdjustments`, and a controlled clock. These tests are distinct from actual provider sandbox validation. UI/browser acceptance, provider approval/evidence gathering, deployment configuration, managed target schema application and live activation remain manual release work. No live provider/payment, production backup/restore or deployment is performed by this implementation.
