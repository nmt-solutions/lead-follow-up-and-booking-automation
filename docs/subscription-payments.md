# Reviewed subscription purchase and paid scope

Issue #44 composes trusted subscription quotes and approved app-owned tax with hosted checkout. It defines the external gateway contract that native Razorpay implements in #45. It does not implement invoices, renewals, refunds, lifecycle changes, proration or reserved worker routing (#46–57).

## Review and checkout

Owners/Admins open **Subscription payments and paid access** from the Business profile or **Review tax and hosted checkout** from Subscription quotes. `prepare` accepts only a quote ID and idempotency UUID. It reads that Business's quote, current billing revision/review and live file availability, effective pricing and current approved tax rules in one restricted PostgreSQL transaction. Lock order is Business → subscription pricing → tax rules. It uses the quote's exact initial line kinds as tax product codes (`subscription`, `reserved_capacity`), quantity one, and integer minor-unit amounts. A customer tax-preview ID, amount, currency or browser status is never an input to payment authority.

The immutable action snapshot copies the trusted quote, actual internal tax calculation, provider/account/mode and intended term. Missing approved treatment is retained as `review_required`, with reasons and a null total. An exact request replay returns the saved action after current actor/Business authorization; changed input conflicts. Historical quote/tax records remain unchanged. The embedded tax calculation retains its `tax_preview` provenance; only the outer action's server-derived quote binding establishes commercial authority.

The customer reviews the saved total, allowances, reach and term, then explicitly creates hosted checkout. `start` repeats current evidence/pricing/rule checks in the same transaction that reserves the provider operation. Changed approval, selected rule, amount, billing evidence or price requires a fresh checkout review. Only one unresolved initial purchase can be started for a Business; an existing paid period prevents another overlapping initial purchase. Upgrade, downgrade and renewal policy belong to later tickets.

Before outbound I/O, the action has a stable operation UUID, immutable financial inputs, a started/pending marker and a random recovery capability. Concurrent/repeated starts do not call `create` again. A crash before the call, timeout after acceptance or result-write failure remains pending and is reconciled by the same operation key. A definitive failure can be reviewed and a separate purchase explicitly initiated; an ambiguous result cannot be silently abandoned for another charge. If the provider cannot establish the outcome, the operator sees the unresolved operation.

## Gateway contract and recovery

`PaymentGateway` in `src/models/subscription-payments.ts` provides `create`, `authenticateEvent` and `reconcile`, plus explicit key/account/mode and currency support. Both web and Trigger compositions use `configuredPayments`. The shipped composition truthfully reports unconfigured until #45 supplies native Razorpay; there is no application-level hard-coded false condition after a supported adapter is installed. Deterministic adapters run the complete financial and paid-access logic against real restricted PostgreSQL.

Native adapter obligations for #45:

- Use the exact durable operation key and immutable financial snapshot. Retain merchant customer, hosted checkout/order, payment and subscription references; use native operation lookup/idempotency, never retry an ambiguous creation as a new charge. Bounded native requests and provider-specific readiness/amount/card/currency checks belong in the adapter.
- Authenticate raw webhook bytes using the actual provider signature and merchant configuration before normalizing an event. Never trust a body Business ID, browser redirect, client signature assertion or subscription-active/authorized-only state as captured-payment authority.
- Normalize stable provider-event identity and a SHA-256 hash of the authenticated payload, plus provider/account/operation/resource references. Preserve the operation binding in native supported metadata or a verified persisted reference lookup. A payment ID and business operation are separate from an event ID.
- Reconcile server-to-server by the durable operation and saved provider references, independently of purchaser membership, browser session or MFA. `confirmed` means authoritative captured/settled payment with exact currency/amount, customer/checkout/subscription/payment identities and intended initial period. Pending/authorized/unknown outcomes do not grant access. Validate native responses and permit hosted URLs only from the provider's documented trusted origins. Optional reconciled checkout details allow recovery of a hosted URL lost after creation.
- Use the explicit quote term. A monthly purchase is one calendar month from the authoritative initial period start in UTC, with calendar overflow constrained (January 31 → February 28/29). A paid pilot uses its configured number of calendar days in UTC. The authoritative initial period starts no earlier than the saved action and contains paidAt; capture can follow the provider period start without shifting paid-through. A native flow needing a different term must make it explicit before acceptance, rather than silently using a 30-day month. Unsupported native period/amount bindings remain review-required.

`POST /api/payment-events` bounds raw bytes, then authenticates/validates through this contract. A receipt commits before reconciliation. Known events bind only to a previously started action by provider/account/operation. Unknown authenticated operations are retained without Business ownership for the reconciliation operator. Reusing an event identity with a changed payload/operation conflicts. Repeated events and distinct events describing the same payment cannot produce duplicate periods. Database uniqueness covers provider/account/event identity, provider/account/payment identity and action-to-period identity.

Confirmation validates all references, exact amount/currency and intended period, then atomically appends the paid period, updates action state and records audit. Confirmation cannot regress after older pending/failed observations. Changed snapshots or mismatched payments stay review-required. Period overlap or a payment already allocated elsewhere cannot produce another grant. Current quote changes after an accepted checkout do not rewrite its agreed financial snapshot. A receipt transaction marks even a formerly failed action for reconciliation, so a crash between receipt and provider lookup is recoverable. An authenticated confirmation hint that disagrees with the provider query stays under review; it grants no access and remains eligible for recovery.

Trigger owns recovery through `reconcile-subscription-payments`. Set the deployment's actual `TRIGGER_PAYMENT_RECOVERY_CRON`; no operating cadence is invented. Recovery scans durable started operations in bounded batches, rotating by last reconciliation time. It never creates or charges again. Identifier/capability-only recovery uses narrow security-definer functions, forced Business RLS and a fresh transaction per action, without impersonating the purchaser. Deploy the worker with the same gateway merchant configuration as the web application.

## Effective scope and consumption

`subscription_period` is the paid financial authority. A restricted membership-aware function exposes only current markets and allowance quantities/units to operational consumers; salespeople do not gain access to legal profiles or financial snapshots. Full payment, event, tax and billing detail remains Owner/Admin or separately authorized platform reconciliation data.

Discovery settings intersect confirmed Business geography, operational source coverage and the paid offer's exact markets. No paid period, explicit zero quantity or mismatched discovery unit removes acquisition availability. Manual run admission and saved-schedule save/revalidation check remaining paid units; actual provider/review reservations atomically consume the configured discovery units under the Business lock. Concurrent runs cannot exceed the period. Reserved/failed/uncertain work remains accounted for; no implicit refund or extra-usage purchase is introduced.

Campaign reach uses that same current reader. Queued sequences recheck campaign reach, the effective paid period and automation units at reservation and at the final provider boundary. Ordinary inquiry/follow-up dispatch also reserves and rechecks current automation capacity. Existing transport permissions, operational caps, pacing, approval, session/MFA, commercial authority, sender and communication-eligibility gates still apply.

The supported outbound automation accounting unit is **`provider calls`**, matching the existing `maxProviderCalls` policy: one reserved outbound attempt consumes one unit. Discovery uses exact equality with the configured `allowanceUnit` and its existing explicit per-operation quantities. Arbitrary commercial units such as “automation actions” are not converted into provider calls; configure a matching unit or implement an explicitly approved additional consumer contract. Zero stays zero. Quantities do not imply guaranteed sends, leads or sales, extra usage, or prepaid Meta credit. Meta remains customer-paid separately.

Incoming inquiry capture, engaged conversations, stored results and human work remain available across acquisition geographies and after paid expiry. Paid automation consumption does not require the inquiry's geography to be in discovery reach. Expiry fences future acquisition and automated dispatch without deleting prior work. The UI retains historical period dates and distinguishes currently active access from a formerly confirmed payment.

## Persistence, APIs and launch inputs

Schema push adds `subscription_payment`, `subscription_payment_event`, `subscription_payment_history`, `subscription_period` and `subscription_usage`, including same-Business composite references, event/payment/action uniqueness and forced RLS. Runtime may update only action execution-state columns; financial snapshots, receipts, audits, periods and usage are append-only. The startup verifier and security reapplication cover these tables. Apply through the parent's configured ROOT `pnpm db-push` before deploying. This child only verifies disposable PostgreSQL, not the deployment target.

- `GET/POST /api/businesses/:businessId/subscription-payments`: saved workspace / prepare financial review.
- `POST .../subscription-payments/start` and `/refresh`: explicit hosted creation / authoritative status reconciliation. A browser return only reloads saved state.
- `GET /api/platform/subscription-payments`: reconciliation-operator queue; `POST /api/platform/subscription-payments/:businessId`: provider reconciliation under current operator grant/fresh MFA.
- `/platform/subscription-payments`: payment detail, immutable evidence/audit, tax/billing links and unmatched authenticated event review.

Live launch still requires #45's native adapter, actual merchant/card/currency activation, real approved prices/units/terms, current reviewed Business evidence, approved live tax coverage, provisioned reconciliation operators and the configured Trigger recovery schedule. No commercial, tax, legal, provider, credential or production activation input is seeded. Browser/UI validation and user acceptance remain pending.
