# Subscription tax configuration and calculation

Issue #43 implements app-owned tax calculation for ADRs 0006/0007. No legal rate, seller registration, production exemption, price or worldwide coverage is seeded. This is internal executable logic, with real persistence; there is no external tax adapter or payment call. The synthetic domestic and international scenarios in `tests/tax.test.ts` are arithmetic and workflow fixtures, not legal evidence.

## Operator configuration

A separately provisioned `platform_operator.tax` grant and a fresh operator MFA session are required on every rules, approval, review-queue and resolution operation. Business ownership or administration does not grant platform authority. Provisioning remains schema-owner administration, as with billing evidence review; runtime cannot provision itself.

From **Billing evidence review**, open **Tax calculation review and rule approvals**, then **Manage tax rules and approvals**. Create a draft with an explicit customer country, optional exact region (blank explicitly covers the whole configured country), purchasing status, currency and product code. Include the jurisdiction, seller registration or documented non-requirement, effective windows, treatment rationale, supporting source/document references and check times. The application validates country codes, UTC instants, windows, positive rate fractions, distinct components, bounds and required reasons. It rejects future evidence check times. A reference records the operator's evidence assertion; the application does not fetch it or establish legal validity.

Taxable treatment requires one or more additive components. Zero-rated, exempt, reverse-charge and export treatments require an explicit approved zero-tax configuration with no rate components. Required customer claims are checked against the current reviewed billing revision. A foreign address, USD currency or Business declaration alone supplies no treatment. Identity review is separate from rule approval.

Saving appends a revision with an expected-version check. Approval or withdrawal appends a decision for that exact revision, with a separate expected-decision-version check, actor, time and reason. Drafts never authorize treatment. Effective intervals include the start and exclude the end. For each rule key and execution mode, the highest version with a recorded decision and a start at or before calculation time supersedes earlier versions. Future revisions wait until their start. A superseding withdrawal, expiry or coverage change does not restore old coverage. Different matching keys are ambiguous; the application never chooses a priority or assumes a country rule overrides a region rule. Withdraw overlapping coverage or approve a corrected revision, then re-evaluate the affected request.

Configuration is explicitly `fixture` or `live`. The deployed composition uses `live`; fixture rules cannot satisfy it. Tests exercise both modes against disposable PostgreSQL using synthetic data. No production legal approval is established by those tests. Operators can configure and approve actual supported live coverage through this same path once the real inputs are available.

## Public application seam and arithmetic

`createTaxApplication` exposes `rules`, `saveRule`, `decideRule`, `workspace`, `calculate`, `reviewWorkspace`, `reviewQueue` and `resolve`. Commands authenticate the actor, validate strict input and use restricted Business-scoped PostgreSQL transactions with current permissions. The clock is injected. There are no mocked internal calculation or persistence modules in its tests.

`calculate` accepts an idempotency UUID, expected current billing-profile/review versions, INR or USD and up to 40 distinct lines. Each line supplies its product code, description, integer quantity and decimal-string unit amount in minor units **before tax**. No price is selected or inferred here. Net values are exact integer multiplication; tax fractions use `bigint` numerator/denominator arithmetic. INR and USD use two decimal places. No monetary value passes through a JavaScript `number` or planning FX conversion.

Each rule explicitly configures half-up, half-even or downward rounding, a 1/5/10/100 minor-unit quantum and per-line or subtotal scope. Rounding applies to each additive tax component. Subtotals group by exact rule revision and component; rounded tax is allocated to lines by largest fractional remainder, with ascending line ID as the deterministic tie-break. Line amounts sum to the stored totals. Inclusive pricing, compounding, signed adjustments, FX and additional currencies are outside this contract; unsupported commercial inputs must be handled by a later explicit extension, never coerced into this calculation.

The command reads the latest billing profile/review and current file lifecycle/retention inside its Business transaction. The Business advisory lock serializes profile/review changes and ordinary file mutation commands. Evidence reads remain read-only for tax operators; cleanup/retention availability is checked at the controlled calculation time. Profile/review version mismatches produce `CONFLICT`; incomplete, conflicting, unreviewed or expired evidence produces a retained `review_required` calculation. Missing approved coverage or ineffective registration likewise requires review. An ambiguous rule set produces conflicting reasons. Review requests have no total, rather than a misleading zero. Both successful and unresolved requests retain their configuration basis, including relevant key history, so later scope changes cannot silently revive obsolete treatment.

Every record copies the original lines, amounts/currency, profile and evidence hashes/retention, evidence decisions, considered rule versions/decisions, selected treatment and rounding, actor, time and reasons. Approved calculations retain exact per-line component tax and totals. All three new tables are append-only for runtime. Later profile edits, reviews, rule edits, withdrawals or file deletion do not rewrite a prior snapshot. Retained file metadata does not promise that the underlying document remains downloadable after its retention deadline.

An exact idempotent retry returns the original record even after current configuration changes. A changed payload under the same key conflicts. `resolve` requires tax-operator authority and creates a linked successor using the original amount/currency inputs and current reviewed evidence/rules. It cannot manually override missing coverage or evidence. A unique same-Business resolution link prevents competing successors. Unresolved successors remain in the queue. The original stays visible throughout.

These records have `purpose = tax_preview`. Customer-supplied amounts do not establish commercial authority. Later checkout/invoicing must obtain trusted agreed quote amounts, call the tax seam against current evidence/configuration, verify currency/line binding and calculated status, and copy the resulting snapshot into its own immutable financial document. An old preview ID or a displayed total cannot authorize a charge or grant entitlement. #42 quote integration and #44 checkout composition are separate work; this ticket has no dependency on #42 and changes no pricing semantics.

## UI, API and database

Owners/Admins open **Subscription tax preview and review history** from their billing profile. The screen preserves input through session/MFA errors, supports multiple lines and displays totals or named review reasons, with expandable original evidence and treatment history. Refreshing saved status retains form entries. Authorized operators open the tax queue, review exact billing evidence, approve supported rules and record a reasoned re-evaluation. The rule editor confirms before replacing an unsaved draft. Business and operator navigation links connect the complete flow.

| Endpoint                                   | Operation                                              |
| ------------------------------------------ | ------------------------------------------------------ |
| `GET/POST /api/businesses/:businessId/tax` | Own-Business history/current evidence; append preview  |
| `GET /api/platform/tax`                    | Authorized unresolved calculation queue                |
| `GET/POST /api/platform/tax/:businessId`   | Authorized history/current evidence; append resolution |
| `GET/POST /api/platform/tax/rules`         | Authorized catalog; append draft                       |
| `POST /api/platform/tax/rules/decisions`   | Authorized exact-revision approval/withdrawal          |

Writes use the existing bounded JSON reader, same-origin checks and safe classified errors/diagnostics. Business IDs and actor identity come from the authenticated scope and validated route, not body claims. Salespeople, foreign Businesses, revoked memberships, reconciliation-only operators and stale operator MFA cannot obtain the corresponding authority. RLS is forced on `tax_rule_revision`, `tax_rule_decision` and `tax_calculation`; runtime receives only SELECT/INSERT. Rules are read internally during authorized calculation, while only relevant configuration is copied to that Business's records. Resolution uses a validated composite same-Business foreign key, applied by the established scoped-key security setup to avoid the pinned Drizzle introspector's referenced-index bug. Repeated schema pushes preserve history. Runtime startup verifies the tables, policies, forced RLS, immutability privileges and resolution constraint.

The parent merger must run `pnpm db-push` in the configured root checkout with its existing schema-owner environment before deployment, then verify the restricted runtime role. This child only applies and verifies disposable test databases, and does not claim target rollout or copy credentials. The schema filter includes all three tables; preparation revokes access before a push and final security setup restores verified policies/grants/constraints.
