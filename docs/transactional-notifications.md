# Transactional notification delivery

Issue #59 composes Better Auth magic links, the existing Business invitation command, operator budget alerts, and selected current operations/subscription notices into the Resend transactional stream. Customer outreach, prospect recipients, campaign content and mailbox synchronization do not enter this stream. There is no arbitrary recipient/body HTTP command.

## Setup and privileges

Provision `platform_operator.notifications` through trusted owner administration. It defaults to false and participates in central privileged-role/MFA classification. Operator commands require current platform MFA and current notification authority. Operations/subscription email preferences additionally require their existing operations/reconciliation capability (a sender-health operator may select operations notices but is restricted to the sender-health source); they do not grant recovery, financial, document or sender-health repair authority.

Configure the same deployment-owned credential set on web and Trigger:

- `RESEND_NOTIFICATION_ACCOUNT`: stable opaque label for the configured Resend team. This is a configuration identity, not a native team ID returned by the usage API. Provision the read, send and webhook credentials for that same team.
- `RESEND_API_KEY`: native sending credential. A sending-only key is sufficient for sending; configuration presence is not proof of permissions or account approval.
- `RESEND_SETUP_API_KEY`: separate full-access credential for native `GET /domains/<id>` and `GET /usage`. Do not expose it in a form or use a Business customer credential.
- `AUTH_EMAIL_FROM`, `RESEND_SENDING_DOMAIN_ID`: exact platform sender and its native domain identity. `COST_ALERT_EMAIL_FROM` preserves the existing budget email sender; configure `COST_ALERT_DOMAIN_ID` when it uses another domain. Both actual senders receive independent native domain verification in the same account snapshot. Keep the original sender for unresolved pre-upgrade invitations and budget alerts.
- `RESEND_NOTIFICATION_MODE`: explicitly `production` or `test_recipient`. The latter permits only `RESEND_TEST_RECIPIENT`; it is an application restriction, not a Resend sandbox or a claim of performed sandbox validation.
- `NOTIFICATION_PAYLOAD_KEY_ID` and `NOTIFICATION_PAYLOAD_KEYS`: independent AES-256 payload key ring. The JSON maps key IDs to base64 encodings of exactly 32 random bytes. Keep prior keys until all payloads using them expire. Keys and plaintext payloads never enter public views, logs or tasks.
- `RESEND_WEBHOOK_SECRET`: native signing secret for `POST /api/webhooks/resend`. Configure the actual email sent/delivered/delayed/bounced/complained/failed/suppressed events in the provider. Registering the route or secret does not prove endpoint deployment.
- `TRIGGER_TRANSACTIONAL_NOTIFICATION_CRON`: explicitly selected schedule for `transactional-notification-recovery`. Deploy/attach it and verify actual executions. Choose a cadence that can recover a ten-minute auth request; the cost-budget schedule remains separately selected.

Open Businesses → Review transactional notification delivery. Select reviewed Free eligibility/limits or exact paid terms, then run **Verify native sender and usage**. This executes native reads with bounded deadlines. Partial domain verification is evaluated using actual SPF/DKIM records and sending capability; independent receiving failure does not automatically stop verified sending. A verified primary sending CNAME can operate while its fallback is pending. Missing privileges or invalid native responses remain actionable setup failures.

Setup observations are fresh for five minutes. A database inspection lease prevents local sends racing the usage snapshot. The durable worker may refresh a stale observation only through the existing approving operator's current notification capability and verified factor enrollment, using the same configured credential binding. Revocation stops that delegation. Live operator changes still require fresh MFA. Provider rate waits also constrain setup reads and subsequent sending.

The operator page shows credential presence, actual native verification, account/mode, usage and independent schedule/webhook presence. Actual native acceptance remains the proof of sending-key access. No fabricated account API, customer self-attestation or permanently unknown quota adapter is used.

### First-login bootstrap

When no notification operator can yet sign in, trusted deployment administration can perform native setup reads without a session. First provision the primary user and its notification operator grant through existing owner administration. Do not invent an MFA factor or mark a session verified. With this checkout's owner `DATABASE_ADMIN_URL` and the deployment configuration above, run `pnpm notifications:bootstrap --operator-user-id <existing-user-id> --terms-file <reviewed-json-file>`. The command requires actual table-owner membership; the application runtime cannot invoke it. It sends no email and grants no account, Business, session or MFA authority.

The reviewed JSON uses the same terms schema as the operator page. For an actually eligible Free account it can be `{"kind":"free","reference":"<reviewed eligibility evidence>","monthlyLimit":3000,"dailyLimit":100,"amount":null}`; choose stricter limits when required. Selected paid terms instead require `"kind":"selected_paid"` and `"amount":{"currency":"USD","micros":"<exact reviewed monthly commitment in millionths>"}` (INR is also supported), with explicit reviewed limits/reference. The command reads the configured native domains and actual team usage, then records auth-only terms. Missing native Free eligibility prevents Free bootstrap. It does not activate a paid plan.

Request the first magic link promptly after successful bootstrap: its native setup observation lasts five minutes, and the auth token lasts ten minutes. Repeating bootstrap refreshes native reads if necessary. Complete normal MFA enrollment, open the operator notification page, save reviewed sending terms from that verified session, and reverify native setup. Bootstrap terms permit only authentication even after MFA enrollment; invitations and platform notices remain held until normal terms supersede them. Sending-key access still requires a real accepted send. This owner command has been tested only against disposable PostgreSQL, not executed against a deployment by this implementation.

## Commercial and usage boundary

Native usage includes all team keys and both sent and received transactional traffic. Its reset instants and rate-limit values are used as returned; receiving quota is not mailbox access. Free-band selection remains capped at the documented 3,000/month and 100/day and at stricter selected/native limits. An account without a native daily Free cap needs explicitly selected paid terms. A null cap never means free service.

Selecting terms does not activate an upgrade or overage. Record the exact reviewed commitment, currency, reference and limits, arrange any intended provider plan separately, and verify actual usage again. The stream does not purchase provider services. Setup/read access and sending privileges remain separate.

Unresolved acceptance remains reserved across retries, held/expired secrets and later rate-limited responses. Historical uncertainty remains visible, while admission reserves only dispatches that can belong to the current monthly or daily quota window. Provider-observed accepted sends are not added again. Native Retry-After/rate-limit headers and current team limits constrain recovery. There is no immediate retry loop.

`operator_cost_native` supplies one stable `native:notification:<attempt UUID>` source for each actual dispatch boundary. It contains purpose, mode, normalized outcome, funding and selected terms, without recipients, content, auth identifiers or payloads. Unknown acceptance stays uncertain, definitive rejection/rate refusal has no new consumed-email quantity, and selected monthly terms are context rather than a repeated per-email expense. Pricing/statement allocation remains with #54; original budget alerts retain their own owner/budget/delegation gate and return actual Resend IDs, never queued-success placeholders.

## Attempts, secrets and recovery

The public auth action retains Better Auth's hashed, one-use 600-second token and generic response on all delivery outcomes. Email remains prohibited as an MFA second factor. A genuinely new sign-in request creates a new notice identity. Durable retry requires its exact pending hashed verification record and original account authority.

The invitation action still persists first and retains its original invitation ID, native key, frozen Business name, recipient, role, expiry and explicit retry semantics. Current inviter authority, revocation and account scope are checked again before I/O. A native receipt can be recorded after authority changes without reviving a revoked invitation or granting access. Team status “provider accepted” does not mean delivered; native stages are available from Team → Review native invitation acceptance and delivery.

Native payloads are frozen before I/O and sealed with AES-256-GCM, authenticated to account, attempt, purpose and source. Database claims and payload access use per-attempt capabilities, trusted database time, current purpose authority and bounded leases. The encrypted payload has its own cryptographic expiry; the expiry-only maintenance helper cannot delete an unexpired payload using a caller's future timestamp. Metadata and immutable event/receipt identities remain after private payload expiry. No legal/audit retention policy is invented for those facts.

First-attempt time and a conservative 23-hour native retry deadline are persisted. Resend guarantees the same key and same payload for 24 hours; the application never extends that external guarantee or creates a replacement key for ambiguous work. Auth expiry can stop retries much earlier. Missing/rotated payload keys, a changed sending credential binding, revoked purpose, expired secrets and expired native guarantees hold/expire work for review. A late actual acceptance is retained against the original recorded dispatch lease even after another lease exists.

The bounded web attempt and the Trigger recovery use this same persisted stream. Cost alerts are recovered by their existing cost worker, which composes the common native adapter and acceptance ledger; the general worker cannot initiate a cost send or bypass their lease/budget gate. Known accepted IDs can be reconciled into the original cost ledger after a crash or expired send window without another provider call. A crash after common acceptance but before cost completion returns the original saved native ID on the next authorized cost attempt.

## Platform producers and status events

Business → Notification preferences and delivery lets a current member choose their own operations email notices. Subscription notices require current Owner/Admin authority. Operator preferences require Notifications plus the respective source capability. A sender-health-only operator receives only health incidents and a direct health destination; this never grants general operations access. Current Business Owners/Admins may select the corresponding managerial health notices even when an operator recorded the incident. Defaults are in-app only. No public form selects another person's email or supplies message content.

Recovery composes current persisted #55 operations notices/escalations (including assigned handoffs and unresolved sender health), plus #46 lifecycle notices. It preserves the immutable source identity and exact stage and does not rerun a mailbox, inquiry, booking, payment or other source action. Current responsibility, membership, policy version, verified account and original source binding are rechecked; acknowledgement, repair, supersession or revoked preference prevents new effects. Lifecycle comparison ignores observation-only timestamps while preserving substantive payment/cancellation/policy state. Existing in-app facts are not relabeled as sent email.

Webhook handling bounds the exact raw bytes and verifies the official Svix contract with `svix-id`, `svix-timestamp`, `svix-signature` and the endpoint secret before parsing. It persists a deduplicated normalized receipt and raw SHA-256 before acknowledging. Raw recipients/subject/content are discarded; recipient/sender digests bind a receipt to the exact saved account/native email ID. A receipt arriving before the POST response remains durable and becomes visible only after that exact native ID is bound. Unknown IDs never acquire arbitrary Business ownership. Received/open/click events do not enable mailbox synchronization or mutate delivery state.

Delivery evidence is projected from immutable receipts. Complaints, bounces, suppression/failure, delivery, delay and sent remain distinct; lower-stage or duplicate events cannot erase stronger evidence. The API response alone establishes acceptance. Delivery means the recipient server accepted the email, not that a person read it.

Resend signs with both old and new secrets for 24 hours after rotation. Prefer deploying the new `RESEND_WEBHOOK_SECRET` during that overlap. Optional previous-secret verification also requires the actual `RESEND_WEBHOOK_ROTATED_AT` and `RESEND_PREVIOUS_WEBHOOK_VALID_UNTIL`, bounded to at most that native 24-hour interval using database time. Remove the old secret afterward and reverify setup for the new binding. Expired previous keys and stale Svix timestamps are rejected.

## Database and validation

Seven managed tables: notification preference, terms, setup coordination, notice coordination, sealed payload, append-only event and append-only receipt. Runtime has independently verified SELECT/INSERT grants and forced deny-by-default RLS; commands/queries use scoped fixed-search-path definer helpers with no PUBLIC execute. Runtime cannot directly read sealed payloads, mutate facts or grant operator roles. Prepare pauses helper/table access; secure restores/validates it. New FKs reference stable primary keys, while existing financial/outbound/document replaceable-UNIQUE reconciliation remains intact. No migration files or capability/customer/commercial seed data are added.

Automated checks use actual disposable restricted PostgreSQL and deterministic external provider fixtures at public commands/queries/events. Owner fixture writes model elapsed database boundaries and revoked authority; runtime expiry always uses database time. UI/keyboard/appearance/viewport/contrast measurements, actual configured target application, provider/deployment acceptance and user acceptance require their respective authorized parent/human steps. No live sending or sandbox execution was performed by this implementation.
