# Selected Gmail synchronization (#29)

Read this contract before changing native Gmail consent, sync/recovery, or activating a mailbox. The shared [mailbox contract](mailbox-processing.md) still governs Business ownership, scope, historical bounds and worker authorization. Gmail workflows use conventional TypeScript; Trigger.dev owns delayed execution and retries.

## Operator setup and launch gates

Production is disabled by default. No private mailbox was read, OAuth consent performed, email sent, provider grant revoked, or worker activated during automated implementation. Deterministic HTTP fixtures exercise the real adapters with isolated PostgreSQL and a controlled clock; this is not live verification evidence.

1. Use an application-owned Google OAuth web client with Gmail API enabled. Record the exact permitted account types and Workspace administrator restrictions. Configure each exact callback: `/api/businesses/<Business UUID>/mailboxes/<mailbox UUID>/gmail/callback` under the configured HTTPS `BETTER_AUTH_URL` origin. Localhost HTTP is supported for controlled development. Google requires registered exact redirect URIs; dynamically invented callback paths do not register themselves. For assisted pilots, register the mailbox-specific URI before connection. [Web-server OAuth](https://developers.google.com/identity/protocols/oauth2/web-server).
2. Complete the applicable brand/scope verification and privacy/data-use review. `gmail.readonly` is restricted; `gmail.send` is sensitive. Server storage/transmission of restricted data brings a security assessment; record the approved assessor/Letter of Assessment and renewal obligation, or the documented applicable exception. Never assume that a testing/internal project qualifies the public product. [Gmail scopes](https://developers.google.com/workspace/gmail/api/auth/scopes), [restricted-scope verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification).
3. Record actual costs and responsibility for verification/assessment, renewal, setup, maintenance, customer mailbox licences, and additional database/runtime/Trigger consumption. These Gmail-specific amounts remain **unpriced**; no universal assessor fee or approval is claimed. The existing [operating-cost baseline](operating-costs.md) is retained. No broker subscription is selected. Obtain and approve the actual quote before launch; a configured flag is an operator attestation, not evidence of Google's approval.
4. Configure server-only `GMAIL_CLIENT_ID`, `GMAIL_CLIENT_SECRET`, `GMAIL_TOKEN_KEY_ID`, and `GMAIL_TOKEN_KEYS` (JSON mapping key IDs to 64 hex characters). Supply keys through the deployment's secret store, retain prior keys while their ciphertext exists, and use a fresh random 256-bit active key. Credentials and PKCE verifiers use the existing AES-256-GCM vault with Gmail/Business/mailbox-specific authenticated context. Calendar settings never configure Gmail. Set `GMAIL_OAUTH_APPROVED=true` and `GMAIL_PRODUCTION_PREREQUISITES_CONFIRMED=true` only after steps 1–3 are recorded.
5. Deploy the mailbox tasks with the same restricted database connection, Gmail settings and keys as the web host. Configure existing `TRIGGER_PROJECT_REF` / `TRIGGER_SECRET_KEY` and set `MAILBOX_WORKER_DEPLOYMENT_CONFIRMED=true` only after deployment is separately verified. Consent queues the initial sync; explicit Sync/Resume can retry it. The delayed poll chain uses current persisted actor/session/MFA and Business membership. Expired team/session authority requires explicit resume by a currently verified manager. There is no app-process timer or broad worker database bypass.

Google testing refresh tokens for external apps can expire after seven days; password changes with Gmail scopes, revocation, administrator policy, inactivity and token limits can also invalidate them. Test both consumer Gmail and each intended Workspace configuration before claiming support. Shared/delegated mailboxes and aliases are not inferred from a display address. [Token lifecycle](https://developers.google.com/identity/protocols/oauth2#expiration).

## Consent, refresh and revocation

Create a Gmail sender identity and save the Mailbox selection first. Reading and sending requests are independent. Google consent requests `openid email` and only the selected Gmail scopes; it does not request Calendar. Effective access requires both the current request and the actual returned grant. Extra previously granted scopes do not authorize processing or sending. Partial send consent does not disable an otherwise granted read permission. This issue adds no email transport; #35 owns sending.

State is hashed, single-use, time-limited, and bound to Business, immutable mailbox, policy generation, actor and exact authenticated session. Token exchange occurs after durable state consumption, outside tenant transactions. Verified Google subject/email must match the selected account; account substitution and unusable tokens are encrypted and quarantined for explicit revocation. Reconnect cannot replace the account binding. Refresh uses a compare-and-swap on credential/generation after current authorization checks; disconnect or another refresh cannot be overwritten by stale network results. No token or private provider payload is returned in diagnostics.

Disconnect durably disables local access and affected follow-ups before calling Google. Failed remote revocation stays visible and retryable; retained inbox/history is readable. Google's revoke operation can invalidate the combined grant for that user/project, including Calendar or other connections sharing it. Separate application read/send/Calendar controls do **not** promise independently revocable Google grants. Other connections recheck access on their next provider operation and may need reconnection. [Combined grants and revocation](https://developers.google.com/identity/protocols/oauth2/web-server#incrementalAuth).

## Selected content and completeness

Gmail metadata is inspected before any body fetch:

- Folder selection is the union of exact Gmail label IDs. Each label is queried separately because Gmail's multiple `labelIds` parameter means intersection. A message must still carry a selected label when read. Thread selection uses exact IDs with `format=metadata`; only individually selected, time-bounded messages use `messages.get(format=full)`. No entire thread body is fetched. [Message list contract](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.messages/list).
- A new label-scoped inquiry must be addressed to the authenticated account and match an Owner/Admin-configured subject phrase. Phrases are case-insensitive text, not regex or model instructions. Selected threads and previously imported threads provide explicit sales context. Whole-mailbox mode processes established threads only; it does not classify arbitrary new correspondence. Empty phrases exclude new label-only inquiries. This intentionally conservative rule can miss legitimate subjects/languages; explicitly select the relevant thread to authorize it.
- Spam, trash, drafts, mailing-list and declared automated messages are excluded. Unknown identity/header/context is excluded before body reads. Supported manual activity requires the authenticated primary address, provider `SENT`, an external recipient and an exact RFC `In-Reply-To`. A SENT observation is not delivery confirmation or proof that a person pressed Send. An INBOX-only selection normally excludes sent messages; label the sent reply with the selected sales label or select its exact thread. No detection is claimed outside the approved selection or time bounds.
- Nested MIME plain-text parts are supported; attachments, forwarded embedded messages and HTML-only bodies are not imported. Unsupported/oversized/malformed content blocks the page with a safe problem; open the message in Gmail and review. HTTP responses, IDs, headers, recipients, MIME depth/part count and body size are bounded. Message text is displayed as text and cannot grant tools, authority, recipients or budget.

History remains off until a separate explicit bounded import. Incremental scans start at the saved new-mail boundary, capture a provider history baseline before enumeration and catch up changes afterward. Opaque history IDs remain decimal strings; page tokens and pending IDs are private persisted checkpoints. Partial pages/retries and overlapping labels cannot create duplicate messages or business effects. [Sync guidance](https://developers.google.com/workspace/gmail/api/guides/sync), [history pagination](https://developers.google.com/workspace/gmail/api/reference/rest/v1/users.history/list).

An expired cursor or invalid continuation triggers enumeration **only from the approved new-mail boundary and within the current selection**. A historical job restarts only within its saved historical time/count allowance. Missing/deleted candidate messages and cursor gaps retain a limited-completeness state even after available mail is recovered: deleted/missing correspondence cannot be reconstructed or called complete. Follow-ups stay paused. After review, the manager may disable reading/save and re-enable/save to explicitly authorize a new boundary; this does not recover or erase the earlier gap/history. A narrower selection cannot prove general reply-route completeness.

The chosen path is polling, not Pub/Sub. Completed incremental work schedules a persisted Trigger continuation after 60 seconds, with idempotent enqueue and current-state authorization. Catch-up/failure states are visible, and reply readiness expires after five minutes without a successful current sync. Quotas/outages use bounded Trigger retries; failed work remains explicitly resumable. Watch expiry, missed watch delivery or a stopped poll chain cannot justify a fresh-completeness claim. No public endpoint accepts arbitrary watch/push JSON. A future push implementation must validate trusted Google signing identity, expected project/service-account/audience, subscription and account-to-Business/mailbox binding before enqueue; notifications alone are not message evidence. Watch renewal, fallback polling and Pub/Sub usage costs would need separate activation. [Watch limitations](https://developers.google.com/workspace/gmail/api/guides/push), [authenticated Pub/Sub push](https://docs.cloud.google.com/pubsub/docs/authenticate-push-subscriptions).

The conservative Gmail classifier cannot prove capture of every reply to a previously unseen campaign thread. Native Gmail therefore does not attest complete general reply-route coverage for #27, even in whole-mailbox mode. OAuth access and a current scoped sync are displayed separately; general sending readiness remains blocked until its complete reply contract is supported. Message-level processing of already imported supported conversations still checks current visibility. Provider label removal updates a separate current metadata observation; original content/provenance remains unchanged, and subsequent automated use follows the latest observed labels.

## Workflow effects and human live checks

Incoming engagement and visibility failures also fence work between durable commitment and the final provider lock, including actions on another channel of the same Opportunity. A previously attempted dispatch remains unconfirmed with the stop reason recorded; it is never relabeled unsent or automatically retried. Only the invocation that acquired commitment and has not yet called its provider can acknowledge a safe pre-provider cancellation.

The final action boundary also checks every associated native mailbox's current visibility for the Opportunity. A newly queued WhatsApp action cannot bypass a disconnected or stale Gmail reply path; restoring sync does not revive earlier canceled actions or hand a human-owned need back to automation.

Incoming mail uses the shared #17/#18 inbox/association transaction. Exact received RFC references and the original channel identity preserve the current Opportunity; names/domains do not merge buyers. New engagement cancels stale pending unanswered work for that Opportunity across channels. Supported sent replies are retained, resolve against the exact received message's current association, and call #19's shared control writer. Replays cannot repeat takeover after handback. Older observations cannot override newer control history. Unmatched sent replies remain visible for review without inventing a buyer; affected visibility stays limited. Restore the exact reference through an explicitly authorized selection/history import before resuming. Existing independent purchasing needs continue.

After all launch prerequisites are approved, an authorized human can perform these controlled checks; this procedure is **not evidence that they ran**:

1. In Business → Mailbox processing, save separate read/send requests, label IDs plus deliberate sales subject phrases (or exact sales threads), and leave history off. Connect the matching Google account as an MFA-verified Owner/Admin. Expect persisted status, no Calendar inference and no old-mail import. Verify declined/partial consent and the other-Business denial path.
2. Have a person create a selected new inquiry and an unrelated/out-of-scope message in a consented test mailbox. Request sync (or observe the separately deployed poll). Expect only selected content in the shared inbox. Explicitly opt into a past UTC interval and small limit, start history and verify the bound survives resume. Check manual replies using a selected SENT label/thread; INBOX alone is insufficient.
3. Associate verified email/WhatsApp messages to one Opportunity and keep another purchasing need separate. Arrange a due test action at the controlled application seam. A new incoming reply must cancel stale unanswered work; a supported manual Gmail reply must show in conversation history and pause the same need across channels until explicit handback. Replayed/reordered events must not repeat those effects or pause the other need. No live sending is activated by this issue.
4. Revoke consent or disconnect. Expect immediate local pause, safe status, stored history retained and remote-revoke retry when needed. Reconnect the original account. Review token expiry/quota/access-denial and cursor-gap cases using deterministic fixtures; do not induce destructive live history loss. A gap must remain visibly limited until a new boundary is explicitly chosen.
5. User-owned UI acceptance: check unsaved-entry recovery for sign-in/MFA, consent/revocation feedback, selected scope, retained reply text, loading/error states and the existing responsive/theme/keyboard behavior. No agent browser, screenshot, CSS measurement, contrast check or preference emulation was performed.
