# Native Razorpay recurring cards

The Next.js payment application and Trigger recovery worker share `configuredPayments`. A supported configured path creates a native hosted subscription link, accepts signature-authenticated durable webhook receipts and polls native subscription, invoice and captured payment resources. The app never receives or stores card numbers, CVVs or mandate tokens. Cashfree, UPI and eMandate are unavailable.

Issue #46 composes the [reviewed lifecycle policy, native Standard Checkout card update, cancellation and in-app notification contracts](subscription-lifecycle.md) into this same adapter and recovery task. Supply `SUBSCRIPTION_LIFECYCLE_POLICY` independently of the merchant account review; missing policy does not authorize grace or cancellation.

## Operator configuration

Set server-only `RAZORPAY_KEY_ID`, `RAZORPAY_KEY_SECRET`, `RAZORPAY_WEBHOOK_SECRETS` (JSON array of one to three current/retained webhook secrets), and `RAZORPAY_ACCOUNT_REVIEW` (JSON matching `src/models/razorpay-account.ts`). Deploy the same credentials, evidence version and recovery cron configuration to web and Trigger. Key prefix must match the reviewed `test` or `live` mode. Native test mode is displayed distinctly and uses fixture-mode approved tax configuration; it does not establish live activation. Native account binding includes merchant ID and mode so test and live receipts cannot collide. No values are seeded.

The account review is **versioned deployment configuration owned by the platform operator**. Access to deployment secrets/configuration is the authorization boundary; there is no Business-editable account approval endpoint or new in-app operator capability. Retain prior reviewed documents in the operator's controlled evidence system. Every action copies its exact non-secret review, version, reviewer, evidence references and effective dates. A new version requires a new checkout review. Never put secrets or card data in evidence references or terms.

The adapter verifies the mapped plan's native `monthly`/interval-one/currency/gross amount and enabled card networks before creating. `GET /methods` reports networks, **not** subscription-method settings, recurring currency approval, fees or settlement. Operator evidence supplies facts that this API cannot establish. The reviewed gross plan must match the server-derived initial payable snapshot and the initial monthly net must match the agreed renewal net. A failed read-only native preflight is retained as a definitive creation-not-attempted state, allowing a new explicitly reviewed action after setup repair. Once a subscription POST is attempted, uncertainty remains recoverable and never permits another automatic create. Never substitute browser financial fields or a different provider. The hosted mandate shows the actual terms and recurring authorization; the app shows the saved cycle count before continuing.

## Native creation and recovery

Creation requires the complete current account review to equal the saved review, including cycle limits and commercial terms. Reusing a review ID/version with changed contents does not authorize a changed mandate.

`POST /v1/subscriptions` sends only the trusted plan ID, quantity one, explicit cycle count, customer notifications and durable notes binding operation, action, Business, financial hash and account-review ID. It sends no invented idempotency header. The action's started marker commits before I/O; a concurrent start, crash, timeout or lost response never repeats creation. Pre-authorization `customer_id` is honestly null. Only the documented exact HTTPS `rzp.io/i/...` hosted origin/path is accepted.

Saved subscription and plan references allow direct lookup. Lost creation uses native `plan_id/from/to/count/skip` listing, 100 entries per sweep, with a durable candidate/cursor. The stable creation window spans one minute before the persisted checkout-start intent through five minutes afterward; it is independent of an earlier quote/payment review time. A full page persists progress; only the exhausted window with one exactly bound candidate can recover a URL. Missing results restart lookup but never permit creation. Multiple candidates or a changed binding remain under review. A delayed creation outside that window is intentionally unresolved for operator investigation; there is no unsafe create fallback.

Invoices are polled in bounded pages of 20, with a durable cursor and periodic restart. Old charges deduplicate by native payment identity. Polling continues for established subscriptions, independently of purchaser sessions and missing webhooks. Provider requests have four-second deadlines, redirect rejection, bounded response bytes and safe classified errors. A damaged/unavailable response cannot become capture authority. Deploy `TRIGGER_PAYMENT_RECOVERY_CRON` and the `reconcile-subscription-payments` task; this code does not claim worker deployment or provider activation.

## Events and paid authority

`POST /api/payment-events` verifies HMAC-SHA256 over the **original bounded raw bytes** using configured webhook secrets, compares signatures in constant time, validates native `account_id`, retains native `x-razorpay-event-id` and a raw SHA-256 digest, and commits only normalized references. Retained old secrets support retried older deliveries. Native webhook processing performs no provider HTTP calls; Trigger recovery reconciles afterward. No card payload or raw webhook body is retained. Reused event IDs with changed bytes/binding conflict. Events without an operation use a unique saved native subscription binding; unknown events retain no fabricated Business or operation UUID.

This path uses hosted subscription links and does **not** install a Checkout callback or trust redirect parameters. No callback signature is used as payment authority. A future Checkout callback integration must implement the documented HMAC over `payment_id|server_saved_subscription_id`; a browser-supplied subscription ID, valid callback or redirect could still only request reconciliation.

Authenticated/activated subscription states, pending/authorized payments and refundable authentication tokens grant no paid period. A positive charge requires a captured, unrefunded card payment; exact payment/invoice/order/customer/subscription/plan/operation bindings; a paid, fully paid native invoice containing one quantity-one plan line; exact reviewed currency and gross amount; and invoice-specific `billing_start`, `billing_end`, `paid_at`. Payment international status must match the supported currency path. Dates never come from a moving subscription `current_start/current_end`. The original subscription start anchors UTC monthly boundaries, including January 31 → February 28/29 → March 31. A conflicting native schedule is held for review, never converted to 30 days. Missing prior periods can be recovered later; they cannot be silently replaced by a later invoice treated as the initial payment.

Native add-on examples conflict with the provider FAQ's deprecation notice. Therefore this card adapter explicitly blocks paid-pilot checkout until a supported separate paid-pilot collection flow is validated; an authentication token does not pay for pilot days. The provider-agnostic application retains its existing configured-days pilot contract. UPI/eMandate and upgrade flows remain separate validation work.

## Frozen financial source for invoices and paid scope

Contradictory paid invoices retain their native invoice reference and a safe review reason even after an earlier cycle was confirmed. They cannot extend access; corrected authoritative evidence can reconcile the same payment without another subscription creation. New renewal tax lookup follows the current reviewed billing country's approved coverage while earlier charge snapshots remain unchanged.

`subscription_period` is the canonical provider-agnostic per-charge source consumed by payment workspace and paid-scope readers. It now allows multiple non-overlapping periods per action, uniquely allocates each provider/account/payment, and stores `charge` (normalized authoritative observation) beside the frozen `snapshot`. No separate unused renewal table is introduced. Fees/fee tax and native INR base amount/currency are retained separately from the customer's gross charge currency; observed base money is not a settlement/bank receipt claim. The provider invoice ID is correlation evidence, **not** an app-issued seller invoice.

The initial snapshot retains the original trusted quote/tax calculation. A renewal retains that original quote's agreed renewal lines, prices, reach and allowances; it evaluates the appropriate effective tax rules against current reviewed billing and retained evidence through a narrowly scoped worker helper. `snapshot.tax` retains input, billing, configuration, lines, totals and calculation date; its renewal purpose is `subscription_charge` with an action ID, rather than falsely attributing a new preview to the purchaser. `snapshot.basis.kind` and exact allowances distinguish initial/renewal consumption. Existing snapshots without `basis` preserve initial behavior. Invoice consumers should parse the exported `paymentSnapshotSchema` and use the frozen period's tax/billing/basis, never latest catalog or action observation. Replayed old payments return their original snapshot even after tax/evidence/catalog changes. New mismatched or unsupported tax bindings grant nothing.

All writes retain forced RLS, Business locks, worker recovery capabilities, scoped financial FKs, immutable financial action columns and append-only period/event/history/usage. Existing prepare/secure pauses financial writes while replacing referenced unique constraints and restores/validates scope FKs. New helper grants and the recovery-column grant are checked individually and restored by security reapplication. No actual configured target database is changed by the implementer; the merger must run the repository prepare/push/secure path using ROOT's environment.
