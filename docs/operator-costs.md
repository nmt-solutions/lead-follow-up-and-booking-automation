# Operator costs and budgets

Ticket #54 supplies a reporting and notification application. It does not change customer prices, tax calculations, entitlements, discovery allowances, approval limits, or dispatch authorization. Global alerts never approve extra spend or cancel customer work.

## Operator workflow

Provision `platform_operator.costs` through the trusted administrator connection. It defaults to false and cannot be granted by a Business. A costs-only operator participates in the central privileged-role/MFA classification. All browser commands and queries require current cost capability and fresh platform MFA.

Open Businesses → Review operator costs and budgets (`/platform/costs`). Select a UTC month, ingest current application usage with an explicit evidence-retention duration, and inspect attribution, pricing, freshness and gaps. Record exact provider statement lines, fixed commitments, optional integrations, provisioning, billing/tax administration, maintenance and setup/support/sales time through **Record or correct attributable cost evidence**. A duration and its evidenced hourly/minute rate can value human effort; an unpriced time record remains visible. No commercial rate or free allowance is seeded.

Use one stable `evidence:` source ID per statement line or attributable allocation. Corrections require its current version and append history with operator, database timestamp and reason. Provider, Business, month, funding and record-kind identity cannot be rewritten by a correction. Allocate shared statements explicitly; amounts represent the recorded platform share. A global statement can list covered native source IDs across Businesses with matching provider/category; Business-specific evidence can cover only that Business. The statement replaces those listed native costs in the total. Another statement cannot cover the same source. Discovery allowance records and authoritative gateway fees cannot be covered this way.

Record future selected-plan changes as signed incremental `plan_change` amounts. They affect the forecast, not incurred cost. An actual attributable charge can cover the planned-change source ID so the forecast does not count both. A decrease uses a negative planned delta; other record types and rates require nonnegative amounts. Preserve the old plan, new selection, effective date and evidence in the source/plan description and reason. Missing amounts remain explicit.

Configure monthly global and category budgets with an explicit INR planning amount, responsible currently authorized operator, delivery choice, delegation duration and optional forecast alerts. The mandated default thresholds are 80/90/100%; they can be configured. Budget/configuration revisions and previously emitted threshold identities remain in history. Revise expired delegation to continue automation. Existing notifications retain their original recipient and identity; authorized cost operators can review/acknowledge the global inbox.

## Native ingestion and accounting basis

`createCostApplication` exposes `workspace`, `refresh`, `record`, `configure`, `setBudget`, `evaluate`, `acknowledge` and the internal scheduled-event seam `recoverPending`. The HTTP surface is `GET /api/platform/costs?month=YYYY-MM` and bounded same-origin `POST /api/platform/costs` commands. There is no customer/global-cost endpoint. Models validate responses before client use. Workspace coverage, category projections, budgets and durable alerts are reusable by #59 notifications and #60 preflight.

Ingestion compares normalized JSON with the latest stable source version and appends only changes. Replaying ingestion does not regenerate AI/search, send customer messages, provision accounts, charge payments or create duplicate costs. The scan timestamp means the application was read at that database time; it is not an external-provider freshness attestation. Native observations carry their actual observation time without an invented validity window. Operator evidence supplies explicit observation/fresh-through dates. Historical records remain available after their freshness date and are visibly marked.

Top-up cash is funding, separate from consumed purchased OpenAI/Gateway credits. Included linked OpenAI credit value and existing-subscription allocation are reported separately from the underlying subscription commitment. The generation's configured funding declaration does not prove which provider balance ultimately paid: coverage explicitly identifies native AI funding awaiting statement allocation. Direct BYOK/provider observations remain distinct from Gateway system fallback. A Gateway system debit counts once; upstream provider cost is context. Reconcile exact statements using covered source IDs instead of adding both request estimates and the same invoice.

Money is retained in original INR/USD millionths. Missing provider amounts can be estimated only from an explicitly configured effective rate and available meters, with the planning-version evidence identified. Reserved/uncertain provider acceptance does not infer a charge. Unknown rates, missing sources and unconverted amounts are not free usage. Workspace fields enumerate estimates, unsettled observations and unresolved funding. No provider billing-fetch contract is guessed: authorized statements/configuration are the production evidence route for commitments, hosting/database/worker meters and other sources without a composed safe API.

Keep each effective rate change in the month's rate configuration. Usage selects the matching exact model before a generic rate, then the latest effective date covering its observation. A rate change does not reprice earlier usage; duplicate model/unit rates at the same instant are rejected.

USD→INR is an explicitly evidenced planning assumption with its check date. It is never customer FX, actual settlement or a bank receipt. With no conversion, original USD values remain separate. The optional linear forecast extrapolates incurred variable monetary usage over elapsed UTC-month time and adds full recorded fixed commitments plus unresolved signed plan changes. This assumes a stable usage/rate mix and complete commitments; it cannot price missing sources or predict unrecorded plan changes. Forecast output includes its as-of time, elapsed/month duration, assumptions and source coverage. It can be disabled.

## Durable effects and security

The in-app notification is committed before email. A database unique identity `(month, category, threshold, actual-or-forecast)` deduplicates across concurrent evaluation, budget revisions, process restarts and Trigger retries. Snapshots preserve owner, recipient, amount, budget and safe message. Acknowledgments and sending/accepted/uncertain/held outcomes append audit events. Provider acceptance is not delivery.

An explicit budget saved with fresh MFA delegates scheduled reporting for its scope. Worker capabilities are budget/month-bound, current-version-bound, expire using `statement_timestamp()`, and require the current owner's cost capability, verified email and enabled/verified MFA factor. No browser session is impersonated. One sweep handles at most 100 current delegations, rotates by scan age and scans a month once. Scope and recipient authority are checked again immediately before email. Revoked owners and expired/superseded delegations cannot authorize new sends. Outcomes already incurred can still be durably recorded using the private lease capability.

[Transactional notification setup](transactional-notifications.md) now supplies the shared native Resend adapter, verified sending domain(s), account usage and selected terms. Configure `COST_ALERT_DOMAIN_ID` if the existing cost sender uses another domain. `COST_ALERT_EMAIL_FROM` retains its original sender and native payload; presence flags alone do not establish sender or account readiness. [Transactional notification setup](transactional-notifications.md) now supplies the shared native Resend adapter, independently verified sending domains, account usage and selected terms. Configure `COST_ALERT_DOMAIN_ID` when the existing cost sender uses another domain. Presence flags alone do not establish sender/account readiness. Set `COST_ALERT_EMAIL_FROM` and `RESEND_API_KEY` for the actual Resend adapter, and choose `TRIGGER_COST_BUDGET_CRON` for `operator-cost-budgets`; deploy and verify that schedule. Neither sender nor cadence is assumed. Missing setup is visible and in-app notifications remain durable. Email uses a frozen payload and stable idempotency key. A two-minute database lease limits concurrent delivery. Ambiguous retries retain that key and stop after a conservative 23-hour window; later recovery holds the notification for review, preserving the in-app record instead of creating a second email identity. Sender changes can make the provider reject a conflicting retry, which remains unresolved rather than silently changing the message.

Six new cost tables use forced RLS with restricted SELECT and INSERT checked independently. Source/configuration/scan/budget/audit records are append-only. Runtime cannot update alert identity, recipient, money, ownership or lease/state columns; narrow helpers own delivery bookkeeping. Every definer has an empty fixed search path, no PUBLIC execute, explicit restricted execute and startup verification. Business context denies global reads; attribution validation checks existing Business/run relationships without exposing customer content. The tables depend only on stable primary keys, so no new replaceable-unique scope dependency is introduced. Existing payment/document/outbound prepare/secure scope reconciliation remains intact.

Discovery adds only nullable `discovery_usage.provider_cost`; current work/operation scope validates the callback and a database trigger prevents rewriting its first observation. Managed prepare revokes and secure restores the specific update grant and trigger. Cost reporting does not alter discovery budget/retry policy.

Retention durations are explicit operational inputs, not legal defaults. Database time computes minimum protected retention and worker expiry; client clocks cannot advance them. Runtime receives no DELETE/TRUNCATE on cost history. No cost-history deletion policy is invented here; #58 can compose reviewed lifecycle policy with the retained timestamps. Actual target application/reapplication belongs to the parent; the child uses disposable restricted PostgreSQL only.
