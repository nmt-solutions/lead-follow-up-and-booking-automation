# Bounded prospect discovery

Issues #10–#12 provide on-demand discovery, consolidation and evidence review at `/businesses/<businessId>/discovery`. Owners/Admins authorize an initial resource allowance; Salespeople can review their Business's retained prospects, runs, request status and public contact evidence. These records remain prospects. No engagement, campaign, recipient approval, outreach permission or message is created. Contact verification here means source-backed role/route classification, not inbox deliverability or permission to contact.

The public application seam is `createDiscoveryApplication`: `start`, `workspace`, `approveAllowance`, `resume`, `cancel` and the trusted worker's `execute`. HTTP authenticates and validates requests using the existing same-origin JSON boundary. Discovery orchestration is an Effect 4 program; conventional hosts use `runPromiseExit` to distinguish expected failure, defects and interruption. Trigger.dev owns the durable `bounded-prospect-discovery` task and its cancellation signal. PostgreSQL owns reservations, results, deduplication and run claims. All protected queries use the restricted runtime, forced RLS and transaction-local Business/actor context.

## Configuration and production gates

There are no default production rates, budgets, markets or result guarantees. `discovery_configuration` is operator provisioned, with no runtime write grant. To provision an **approved** Business policy, supply a private JSON file containing `businessId` and `policy`, then run `pnpm exec tsx scripts/configure-discovery.ts <file>` using the configured schema-owner connection. The schema validates:

- `adapterId`: the approved adapter profile; it must match the actual composed provider.
- `activeMarkets`: effective authorized reach, separately from customer-selected geography. Exact configured market names must match confirmed Business markets.
- `coverage`: explicit `{ market, source: "public_web" }` entries. Unsupported markets cannot run.
- `allowanceUnit`, `maxRunBudget`, `searchUnits`, `reviewUnits`: actual approved resource units and maximum reservation per operation. These are resource allowances, not invented currency prices. A future live adapter must bound its transport/model work to each reservation, disable hidden retries, and supply configured commercial limits before activation.
- `concurrency` (1–4), `maxResults` (1–10), `deadlineMs` (100–120000): bounded execution settings, not promised output counts.
- `permissions`: confirmed `retainEvidence`, `displayEvidence`, `exportEvidence`, `afterCancellation`, `privateAiContext`, plus explicit `retainQueries`. Required rights must be true. They must reflect the executed order and approved AI data scope, not an inference from self-serve terms.

The brief snapshots saved offering, specifications, order/delivery/service requirements, reviewed buyer categories, exclusions and selected eligible geography. The owner separately reviews a public offering phrase. Only that phrase, buyer category and market go to the search port. Private files, mailbox content and approved knowledge are not retrieved or sent. The AI review port receives only the invocation's brief and shortlisted source content under its approved private-context scope.

**Live execution is not activated by this implementation.** `configuredDiscoveryProvider()` returns unavailable until the selected Exa/AI adapter is implemented in #16 with approved contract/configuration from #2. There is no live or fixture fallback in production. Deterministic ports are injected into the real application/persistence tests, using explicitly named fixture credits. `TRIGGER_PROJECT_REF` and `TRIGGER_SECRET_KEY` gate task submission, and the task must be deployed before activation. Missing configuration is visible in the UI/API. No live provider calls or production result counts are claimed.

## Spending, cancellation and recovery

Each operation commits its reservation in a short, Business-locked transaction **before** the external call. Concurrent fibers and workers share that persisted authorized bound. Provider work runs outside SQL transactions. Every new reservation rechecks current actor session/MFA, membership, targeting and coverage, including an authoritative assurance check on the transaction connection after acquiring the Business lock. Page/model content cannot select tools, recipients, authority or allowance. Expected provider failures must use `DiscoveryProviderFailure`; unknown exceptions are defects. External responses are validated, evidence quotes must occur in the source, and URL credentials/query parameters/private hosts are rejected. A request date needs its own exact source quotation containing that ISO date; a known status needs an explicit `Status: open` or `Status: expired` source marker. Unsupported date/status claims remain unverified/unknown; an open request also needs its evidenced date. These facts retain their supporting quotations with the source URL and check date.

Partial matches, usage and stop reasons persist incrementally. Uncertain/failed operations consume their reservation; there is no automatic increase, refund-and-retry or provider fallback. The runtime cannot change the snapshotted policy, brief or original authorizer. Only explicit scoped commands increase the allowance or rotate the execution capability. Results consolidate by scoped exact identities and purchasing needs, retaining every accepted review observation. Query text is persisted only under `retainQueries`; raw pages/provider exceptions are not retained in diagnostics. Public projections exclude worker capabilities and session IDs.

Interruption aborts **and joins** owned provider work. An already-running SQL transaction is awaited before the Effect scope returns; its completed commit may remain, but it cannot authorize a later provider call. Mixed cancellation and cleanup defects remain defects. Completed evidence is retained, reserved calls become uncertain, and stopped runs cannot spend again without an explicit authorized resume.

Trigger retries are disabled for billable execution. Duplicate deliveries of queued work claim once; a claimed run never blindly repeats calls. Lifecycle failure/cancellation hooks terminalize lost work through a narrow capability that only stops the matching run. If a hard process/database failure prevents the hook too, the last persisted queued/running state remains visible for operator reconciliation; do not reset it or replay an uncertain call. Re-delivery of a queued request uses the original request key and task idempotency key. Any new run requires a separate allowance authorization. Recurring schedules and the live provider adapter remain successor issues.

## Allowance approvals and explicit recovery (#13)

The run view separates total authorized allowance, consumed units (successful, failed and uncertain operations), outstanding reservations and unreserved remaining units. `used` remains the total of consumed and reserved units. Results, completed search groups, current stop reason and append-only allowance/recovery history stay available. Units authorize research capacity; no configured currency, price, charge or invoice is inferred. Commercial pricing remains outside this workflow.

`POST /api/businesses/<businessId>/discovery/allowance` accepts `runId`, a UUID `requestKey`, `expectedBudget`, a strictly greater total `budget`, and `confirmExtraUsage: true`. A current Owner/Admin with verified Business MFA must authorize it. The stopped run's snapshotted `maxRunBudget` bounds its total, including every increase. A Business-locked transaction checks current session/factor, membership, targeting, policy, prior allowance and request identity, then commits both the new total and attributable audit entry. Competing approvals against the same previous total cannot both apply. Replaying the identical request returns the saved action; changed fields/actor/session conflict. Increasing the allowance does not enqueue work.

`POST .../discovery/resume` accepts `runId`, a fresh UUID `requestKey`, `expectedAttempt` and `confirmResume: true`. It independently checks current authority and setup, then rotates a stopped run's private execution capability and binds it to the current approving session. The original run ID, authorizer, brief, results and usage remain. Every resume records its actor, time, prior stop and allowance. Old tasks and lifecycle hooks cannot mutate the new attempt. Duplicate queue deliveries claim once; task idempotency includes the attempt capability. Ambiguous queue submissions stop conservatively; another explicit resume with a new request is needed to recover them.

Successful searches retain bounded, schema-validated source snippets as internal checkpoints under the configured evidence permissions; they are never public response fields or diagnostics. Stable logical step identities and a unique run/step/attempt constraint prevent duplicate reservations. Successful search/review steps are reused, not called again. Remaining reviews keep the original buyer/source and consolidation path. Failed or uncertain calls remain consumed, and retrying one creates a new operation reservation within the same run's remaining allowance. There is no automatic Effect, provider or Trigger task retry, budget reset, refund, hidden fallback or extra bill. An explicit resume can reset the execution deadline, but cannot reset usage or increase the snapshotted total cap.

`POST .../discovery/cancel` accepts `runId`, UUID `requestKey` and `expectedAttempt`. It requires current Owner/Admin authority and MFA, stops new reservations, records cancellation and settles outstanding reservations to consumed uncertain usage. Already reserved external work may still finish; it cannot append results to a cancelled or later attempt. Task cancellation/interruption still aborts and joins owned work through the existing Effect boundary. A cancelled run only continues after a separate explicit resume, with the uncertainty and cost explanation shown beside the action. If an entire worker and its recovery hook are lost, an authorized cancellation can settle that persisted state before explicit recovery.

The additive schema adds `discovery_command` (insert/read only) plus nullable checkpoint/attempt fields on usage and attempt/progress fields on runs. All new data uses forced Business RLS and restricted column grants; original configuration, policy, brief and authorizer remain protected. `pnpm db-push` installs the schema and reapplies/validates grants, policies and the narrow terminalization helpers. Existing evidence and identities are preserved. Stopped legacy runs lacking checkpoints cannot safely resume; their UI explains this, retains their results and permits a separately authorized new run. No backfill invents missing source content or operation identities.

## Verification and user workflow

### Consolidation and refresh (#12)

`discovery_prospect_alias` persists Business-scoped exact identity aliases; `discovery_observation` appends each accepted review under its reserved operation ID. Both are insert/read only for the restricted runtime, with forced RLS and checks linking their Business to the referenced prospect/run/operation. The original `discovery_result` snapshots remain intact. The old source-URL uniqueness index is replaced by a nonunique source index so distinct needs on one page can retain different identities. No records are deleted or rewritten. Older results are read conservatively as legacy observations and adopted on an exact match; unavailable historical raw/duplicate metrics are not invented.

An optional provider `company: { name, website, quote }` requires the complete source statement `Company name: https://company.example/`, with the exact supplied name and safe HTTPS website origin. This narrow identity contract applies to organizations and sole proprietors, never personal-use consumers. Matching uses the normalized exact company name and website origin, buyer identity/use, market and need. Without this evidence, only the exact source URL and source name can establish the same identity. A request need includes the exact normalized quotation, evidenced publication date and source URL. Cross-source request matching additionally requires an explicitly evidenced `request.reference: { url, quote }`, supported by the complete source statement `Request URL: https://company.example/rfq/123`. Identical wording/dates alone cannot merge independent RFQs. Distinct references on one source also stay separate. Potential-fit records use the offering and all saved requirements. Status, role and check dates can change without changing an otherwise identical need. The stable source/name/need alias survives newly established company or reference evidence, while contradictory existing identities are kept separate for review. There is no fuzzy matching, inferred shared-domain ownership, matching-confidence threshold, expiry age or automatic enrichment. Unsupported identity formats can leave separate prospects for human review. Ambiguous collisions withhold role/open-demand certainty rather than silently merging established identities.

Contact identities are scoped to the Business and evidenced company (or exact source and prospect name), normalized contact name and exact public route. Changing a role retains the same contact identity when name/route remain the same; establishing company evidence preserves an already retained contact identity. Different routes are not assumed to be the same person. The current projection deduplicates contact identities and preserves their original source observations in history. Changed or unverified roles never inherit historical buyer coverage. Conflicting current role claims withhold purchasing responsibility; conflicting request status/date/expiry claims withhold established open demand. The original claims and uncertainty stay inspectable. No review-resolution workflow or certainty override is introduced.

Successful review operations also record safe source URL/check time, even when they retain no match. A unique Business-scoped check ordinal is allocated under the existing Business lock and breaks equal-clock ties; command replay cannot increment it. The latest successful run checking a source supplies its current observations; observations from earlier checks remain historical. A later review that no longer establishes a consumer's explicit need removes that need from established open demand, including when the controlled clock has not advanced, without deleting its grounding history or inventing an expiry. Failed/interrupted checks cannot establish a successful revalidation. Unchecked sources retain their actual dates, with no invented freshness interval. Request expiry still uses only evidenced source expiry and the controlled application clock. Run views preserve their own observations; the Business-level retained view uses history across all runs, including those outside the 50-run display window.

Run metrics distinguish raw search entries (including exact duplicates and rejected matches), accepted match observations, retained unique prospects, newly created identities, first refreshes of existing prospects in that run, and further duplicates in that run. Exact repeated search entries skip redundant review; different evidence/needs on the same URL are reviewed separately. Every accepted duplicate retains its provenance. Replaying the original command/task adds no provider work or observations. A separately authorized new run spends its own search/review reservations and records its new checks, even when retained identities/counts are unchanged. These measurements describe research, not engagement or permission to contact.

### Request status and contact evidence (#11)

Results retain their run-specific evidence in the existing `discovery_result.data` JSONB column. This is an additive document-format change; no table/column migration or backfill is required. Reads and writes validate the persisted document. Older #10 snapshots default to no contacts and no expiry evidence; they never acquire invented buyer coverage. Source URLs, quotations, check times, buyer category, request facts and uncertainty remain available in the application/API for later workflows.

Each run projects two disjoint sections: **Open buying requests** and **Potential buyers**. The first requires an explicit relevant public need, an evidenced publication date no later than the check date, and the existing exact `Status: open` source marker. The second retains other evidence-backed matches, including expired, undated and uncertain requests. Personal-use consumers require the supporting explicit request even when it is undated, expired or uncertain. A general suitability quotation alone does not qualify. The conservative English request recognizer accepts direct need/seeking/buying statements and RFQ/RFP labels; unsupported wording cannot establish an explicit request.

An optional source-declared `expiresAt` ISO timestamp requires its own complete explicit `expiryQuote`: `Closes <timestamp>`, `Expires <timestamp>`, `Deadline: <timestamp>`, `Request closes at <timestamp>` or `Request expires at <timestamp>`. A last-updated timestamp is not an expiry. Request and status declarations must also be complete source statements; a truncated/negated need or a prefix of a longer status cannot establish open demand. The controlled application clock projects a request as expired when the evidenced timestamp is reached, preserving the original observed status and expiry evidence. Without such evidence there is no invented expiration age or revalidation interval. The UI labels the source check time and explains that refresh reloads saved observations, without performing a fresh source check. No status establishes direct engagement.

Provider reviews may supply up to five contact candidates. Each candidate has nullable `name`, `nameQuote`, `roleEvidence: { role: "purchasing" | "owner", quote }` and `route: { kind: "email" | "phone" | "contact_form", value, quote }`. A retained contact also records the source URL and check time. Unknown/unsafe/malformed candidates are omitted without dropping the strong prospect. Emails must be syntactically valid, phones use an explicit international number, and form URLs use the existing safe public HTTPS evidence-URL restrictions. Exact source quotations must support the name and complete route value. A substring of another address is not a usable route.

Purchasing responsibility requires a complete explicit source declaration tied to the name, such as `Mira Shah: Head of procurement`, `Mira Shah is the purchasing manager.` or `Arun Rao: Owner`. The supported title vocabulary is deliberately conservative (purchasing/procurement leads/managers, buyer, explicit purchasing/supplier-selection responsibility, owner/co-owner). A model's asserted role, another employee's title, a negation or a truncated statement cannot establish it. Unsupported formats remain unverified; no enrichment fallback is enabled. A **Buyer contact** additionally requires the same name explicitly attached to the route (`Name: address` or `Name — address`); an unrelated public mailbox remains a **General business contact**, even if an owner is known. A named buyer without a usable route remains visible with **Missing contact**.

Counts are calculated from unique persisted prospects **within each run**, never by summing repeated runs or counting multiple contacts on one prospect. `evidenceBacked` covers both sections; `potentialBuyers` and `openBuyingRequests` partition that total. `contactable` counts any usable public route, including general business routes. `namedBuyers` counts prospects with an evidenced named purchasing person/owner, including those without a usable route. The two coverage measures can differ in either direction. None counts outreach permissions, engaged leads, conversations or outcomes.
