# Customer-owned WhatsApp onboarding

Issue #38 implements direct Meta Cloud API Tech Provider onboarding under ADR 0008. Business Owners/Admins with current MFA use **Business → WhatsApp identity**. No BSP, platform credit line, prepaid Meta credit or message sending is activated by onboarding. Separately authorized signed intake and durable recovery are described in [WhatsApp intake](whatsapp-intake.md).

## Ownership and billing

The Business records its Meta portfolio ID, international number, existing Cloud API / Business App / assisted-new-number path, and actual provisioning/control/transfer terms. Explicit acceptance records customer control and direct customer-paid Meta billing. These are declarations, separate from provider evidence. Assisted setup does not purchase a number, grant carrier control or promise a transfer. The customer must retain the SIM/OTP, carrier and Meta administrator access under its recorded arrangement.

The Business pays Meta with its own payment method. Our subscription and automation allowances exclude Meta usage; the same customer-paid charge is excluded from operator spend. The onboarding query exposes that billing classification explicitly. Quotes, usage accounting and messaging policy belong to their own tickets. Prices are linked to Meta instead of copied into defaults.

## Operator configuration

All settings in `.env.example` default to unavailable. Record actual platform business verification, Tech Provider access verification, App Review/Advanced Access and a published app before setting the four approval flags. Configure the selected app ID/secret, Facebook Login for Business Embedded Signup configuration ID, supported Graph version and AES-256-GCM key ID/JSON key map (64 hex characters per key). Register the application's actual HTTPS domain and SDK/login configuration at Meta. Configuration is server-only; the browser receives the public app/config IDs and Graph version only after an authorized start command.

Embedded Signup uses v4, session info version 3 and a one-use authorization code, exchanged immediately on the server with the empty redirect URI used by Meta's JS SDK example. The local state expires after ten minutes and binds the Business, connection version, actor and exact authenticated session. Incomplete `FINISH_ONLY_WABA`, missing assets, errors and cancellation persist an incomplete state. Browser asset IDs are hints: the server debugs the token, verifies the expected app and permissions, checks the customer's owned WABAs and verifies number membership and the expected phone number through Graph.

Required permissions are `business_management` (customer asset ownership check), `whatsapp_business_management` and `whatsapp_business_messaging`. Missing/revoked permissions, expired tokens, stale evidence, account review, Business verification and unregistered/unverified numbers remain separate blockers. A verified but unregistered Cloud API number can be registered by an explicit customer action with its six-digit PIN. No PIN is stored. Ambiguous registration clears proof and requires a read-only status refresh before any retry.

Customer tokens are encrypted with Business/connection/version authenticated data. Keep historical keys during rotation. Public responses/audit diagnostics never contain authorization codes, tokens, PINs or provider payloads. Owner/Admin checks and session/MFA validation run on each scoped transaction, including after external I/O. Customer account-administration reads are restricted to Owners/Admins; the separate platform review workspace requires the dedicated reviewer capability. RLS, restricted column grants, tenant-scoped foreign keys and an exclusive number binding back those boundaries. No tenant transaction remains open during Graph requests.

## Coexistence and readiness

Business App requests use `featureType: whatsapp_business_app_onboarding`. They remain unavailable unless the operator has actually approved that onboarding path. A normal `FINISH` cannot establish coexistence: the provider must return `FINISH_WHATSAPP_BUSINESS_APP_ONBOARDING` and the selected number must report `is_on_biz_app: true`. Unknown, unsupported, mismatched or incomplete cases cannot appear ready. The UI does not promise all Business App features, history import or manual-app activity capture. The deterministic fixture tests this exact completion/inspection path; it is not live account validation.

`onboardingReady` requires every independent current check and configured operator prerequisite. Provider observations expire within five minutes for the Graph adapter and never outlive a known token expiry. Failed refreshes invalidate older positive provider proof. The Graph adapter deliberately reports **customer payment method: not verified**: a valid token, message health or customer declaration cannot prove which payment method or credit arrangement Meta bills. The separate assisted review below supplies account-specific evidence without inventing a payment-ownership API. The actual configured Graph adapter is tested with deterministic HTTP responses and separately reviewed evidence, reaching onboarding readiness while automation remains unavailable.

[#39 intake](whatsapp-intake.md) and [#40 sending](whatsapp-sending.md) add separate `inboundReady`, `manualVisibilityReady` and `sendingReady` evidence. The configured native sending adapter and actually deployed outbound worker can attain account sending readiness with current onboarding, incoming and supported manual visibility. Account authorization does not establish recipient permission, approved templates, customer-service windows, paid automation, history synchronization, human takeover or delivery evidence. Every action repeats its independent current checks; onboarding does not itself send a message.

Disconnect removes local credentials, effective proof and pending callback eligibility while preserving immutable review history. It leaves the customer account and number intact, without deregistration, transfer, WABA-wide unsubscribe or removing other providers. The Business can separately revoke the app through Meta Business settings. Saving changed terms or starting a fresh connection invalidates previous local proof; the append-only event log retains the accepted terms and safe operation history.

## Assisted control and direct-payment review

Provision `platform_operator.whatsapp_review = true` through the operator administrator's restricted database process for the intended reviewer user ID. There is no customer-facing grant command or environment readiness toggle. This capability is integrated with central privileged-role classification, session, MFA status/readiness and `whatsapp.review` capability checks. Only a reviewer **outside the customer Business** with a current session, verified current authenticator and MFA younger than 15 minutes can read or append reviews. History records reviewer ID, authenticated session reference (not returned publicly), server time and monotonically increasing evidence version.

1. The customer saves actual control/transfer terms, authorizes the selected portfolio/WABA/number and obtains current provider ownership, permission and number-verification observations. In **Business → WhatsApp identity → Customer control and direct Meta payment**, they find their Business ID, exact selected assets, review status/history and next action. They show redacted control records and Meta payment settings identifying their Business as direct payer to the onboarding operator through the agreed secure support channel. Never collect card numbers, CVVs, OTPs, tokens or full payment documents in application fields.
2. The reviewer opens **Businesses → Review WhatsApp evidence** (`/platform/whatsapp`), enters that Business ID and matches the displayed connection version, customer portfolio, WABA, number ID and international number to the records. Verify customer control of these exact assets and the customer's own direct-payment arrangement at Meta, with no platform credit line or paid BSP payer.
3. Retain the exact redacted records in the agreed access-controlled case archive. Enter a non-secret uppercase case identifier for each record (for example `META-CONTROL-2026-001` and `META-BILLING-2026-001`), its lowercase SHA-256 digest and the time the facts were observed. References/digests are validated identifiers, not uploaded contents or credential-bearing URLs. Digests identify the artifact; the authorized human establishes the facts. Observation times must be within the current saved-terms period and not in the future. Explicitly choose an expiry appropriate to the reviewed evidence and confirm all three reviewed facts. No default validity period or automatic renewal is supplied.
4. **Record evidence review** appends immutable approval bound to Business, connection ID/version, configured provider key, exact portfolio/WABA/number and requested number. POST `/api/platform/whatsapp/{businessId}` uses `action: approveEvidence`; GET reads the protected workspace. Customer account commands cannot dispatch review actions. Repeated/stale evidence versions conflict rather than append twice. Current authority/session/factor/MFA are rechecked on the transaction; INSERT RLS also enforces reviewer grant, exact session/current factor and 15-minute MFA.
5. The customer reloads saved status. The Graph observation remains `customer_payment_method: unknown`; separate `paymentEvidence` reports assisted-review provenance, validity and history. Effective review can resolve that **unknown** payment check. Explicit missing/unsupported payment results and all other provider/setup blockers remain independent. Onboarding can become ready; incoming/manual capture requires its own #39 evidence and sending requires the independent #40 configuration and action checks.
6. **Revoke review**, a reason and confirmation append revocation of the exact approval (`action: revokeEvidence`). Expiry, malformed evidence, changed scope/version/provider, reconnect or disconnect invalidate effective proof at query time. The newest approval is authoritative: revoked/expired approvals never fall back to older ones. Renewal requires another explicit review. History survives these changes and schema/security reapplication. Revoking an operator grant prevents future reviews; it does not erase historical reviews. Revoke affected evidence explicitly when its reliability changes.

The secure support channel, evidence archive/access/retention policy, legitimate source records, reviewer assignment and evidence-appropriate expiry remain live operating inputs. Recording identifiers without inspecting the referenced account-specific records is not a completed review. Deterministic tests do not establish live Meta billing inspection.

## Database and verification

Schema additions: `whatsapp_connection`, `whatsapp_oauth`, `whatsapp_event`, append-only `whatsapp_evidence`, and default-false `platform_operator.whatsapp_review`; no backfill or destructive migration. Evidence has forced RLS, tenant/connection foreign keys, unique Business/evidence versions, exclusive approval-or-revocation records and SELECT/INSERT-only runtime grants. Security setup restores policy expressions and strips table and column mutation grants; runtime verification fails closed on unsafe privileges. Run the configured `pnpm db-push` on the reviewed integration schema during rollout. The test harness applies and reapplies the complete schema to disposable PostgreSQL, secures the runtime role and runs public application commands against real restricted persistence.

Automated coverage uses deterministic Meta responses, a controlled clock and real authentication/MFA. No live Meta sign-in, number registration, billing change, coexistence/historical sync or message send is asserted. Browser/UI validation and human acceptance are pending.
